# Landing page, first-visit routing, and SEO

How `/` serves two different things, what the middleware decides, and the rules governing landing-page copy and structured data.

Moved out of `CLAUDE.md` (2026-09-12) to keep the always-loaded file small. Content is unchanged -- these are the as-built notes, so prefer them over re-deriving a rule from the code.

### Landing page + first-visit routing
- **`/` serves two different things, and the middleware decides which.** A first-time visitor gets the marketing page; anyone who has already reached the product — or is signed in — is redirected to `/explore`. The whole rule is `applyFirstVisitGate()` in `lib/landing/first-visit.ts`, called from `proxy.ts` after `updateSession()`. Constants (cookie name, the `?ref=app` marker, `isProductPath`) live in `lib/landing/nav.ts`, which is deliberately free of `next/server` imports so a Client Component can import `LANDING_HREF` without pulling the server runtime into its bundle.
- **The gate belongs in the middleware, not the page.** Reading `cookies()` in the Server Component would opt `/` out of static generation — the last thing a marketing page wants — and Vercel runs middleware *before* the CDN cache, so the redirect still fires on a cached route. Crawlers carry no cookie, so **Googlebot always gets the landing page**; that is what makes the SEO work.
- **`wr_seen` is written CLIENT-SIDE by `<MarkVisited>` in the `(app)` layout, not by the middleware.** It used to be a `Set-Cookie` on any request to a product path, and that was wrong: **Next prefetches every `<Link>` that scrolls into view**, so merely *reading* the landing page fired requests to `/explore`, `/hub` and `/add` and marked the visitor as a product user — bouncing them to Explore next time they opened `/`, having never chosen to go there (fixed 2026-08-04). The header that identifies a prefetch (`next-router-prefetch`) is **not visible to the proxy** — Next strips it; the proxy sees only `accept`, `host`, `user-agent` and the forwarded set. `accept` does separate a document load from a prefetch, but a *client-side navigation* looks like a prefetch on that axis too, so keying on it would miss anyone clicking the hero CTA. An effect only runs when React actually renders, which is exactly the line wanted. Cost: the cookie can't be httpOnly. It holds no secret, and a crawler never gets it — which is what we want anyway.
- **Which screens count is decided by where `<MarkVisited>` is mounted** — the `(app)` layout: explore, hub, add, vendor, recon. `/terms` sits outside it deliberately (linked from the landing footer; reading the disclaimer shouldn't suppress the pitch), and so do the `(auth)` screens — visiting a login form isn't using the product, and anyone who completes it is caught by the signed-in check instead.
- **`/?ref=app` always renders the landing page.** Without an escape hatch the page is unreachable from inside the app — every link back would be bounced straight to Explore by the gate, because anyone clicking one has the cookie by definition. Both in-app links (`BrandFooter`'s lockup, `ProfileMenu`'s "About Wedding Recon") use `LANDING_HREF`, and so does the landing header's own wordmark. **Never link to a bare `/` from app code.**
- **A redirect response starts blank.** `NextResponse.redirect()` does not inherit the cookies `updateSession()` just wrote, so the gate copies them across; drop that loop and a session silently fails to refresh on any visit to `/`.
- Query strings survive the redirect on purpose (`/?types=venue` → `/explore?types=venue`), which is what lets a campaign link deep-link a filter.
- **Signed-in beats the cookie.** `updateSession()` now returns `{ response, claims }` instead of just the response, so the gate recognises an account holder on a new device or after a cookie clear at no extra cost — the `getClaims()` call was already being paid for on every request.

- **`/` is no longer the only marketing page.** `/for-vendors` (2026-09-20) is the vendor-side one; see `docs/notes/admin-and-portal.md`. It reuses `LandingHeader`/`LandingFooter` and the shared `Section`/`SectionHeading` in `components/landing/section.tsx`, which were extracted from `app/page.tsx` when the second page appeared - two marketing pages that disagree about gutter and column width read as two different sites. Its copy follows the same contract in `lib/vendors/content.ts` (no em dashes, US spelling, price never hardcoded). Unlike `/`, it carries no JSON-LD - it had an `FAQPage` node until the FAQ itself was cut on 2026-09-20, and structured data for content a page does not render is a violation. The first-visit gate does not touch it: only `/` is decided there.

### Landing page content + SEO
- **All copy lives in `lib/landing/content.ts`**, not in JSX — every string, including section headings and the app-visual mock-ups. `FAQ_ITEMS` renders the accordion *and* the `FAQPage` JSON-LD, hence `answer` is a plain string: structured data cannot carry markup, and Google treats a visible/structured mismatch as a violation. The file opens with the editing rules; the two that bite are **no em dashes** (spaced hyphen instead, matching the enrich pipeline's own gate) and **US spelling**.
- **Page shape** (2026-08-04): hero → how-it-works stepper → four problem/solution rows → quick-facts deck → FAQ → CTA. The stepper owns `#how-it-works`, which the header nav anchors to; the hero's secondary CTA to it was removed, so that nav link is now the only thing holding the anchor alive.
- **The quotes in `PROBLEM_SOLUTIONS` are real people**, reproduced verbatim, consented to under first name + year + town (Kiara, 2026-08-04). Do not paraphrase, and do not let one name a vendor: no business is identified, which is what keeps an unflattering account a personal experience rather than a claim about a named business.
- **The FAQ is native `<details>`, not the Base UI `Accordion` used everywhere else.** The accordion unmounts a collapsed panel, so the answers would be absent from the HTML a crawler reads. `<details>` also needs no JS, which keeps the entire landing page a **zero-client-bundle Server Component**.
- **Nothing on the page is fabricated about a real business.** The hero's example recon card and the `AppVisual` mock-ups carry no vendor name — `place` is a county, never a business a reader could go and check. The "Example" badge was dropped as redundant (Kiara, 2026-08-04), so that anonymity is now the *only* thing marking those figures as illustrative. An invented quote attached to a named vendor would be a fake review of someone's livelihood — the same line the enrich pipeline draws with "negativity: sourced only, never synthesized."
- **App visuals are drawn in code** (`components/landing/app-visual.tsx`), not screenshotted: sharp at any size, no bytes, and they take their colors from `CATEGORIES` so they cannot drift from the real map. That file carries the swap point for real screenshots — capture those from a session with DB credentials, and look at what is on screen first, since a screenshot reads as authoritative in a way an illustration does not.
- **Stat figures are static constants measured 2026-08-01** (`DATA_SECTION`, `VENDOR_COUNTS`, `BEAUTY_SETUP`), sourced from `docs/vendor-filters-proposal.md` — deliberately not a live query, which would drop static generation on the one page that most needs it and render "0 vendors" whenever the free tier pauses. **Every derived percentage ships with its denominator.** Only quote a rate when BOTH answers get recorded: most booleans in that proposal ("shoots film", "BYO alcohol") are one-sided detections where silence means unknown, not no, and publishing one as a rate asserts something false about every undetected vendor. The hair-and-makeup split qualifies; that is why it is the one on the page.
- **Chart color was computed, not chosen.** The dataviz skill's palette validator rejected the ten category hues as bar fills — planner green vs food amber is ΔE 1.5 under deuteranopia, dj vs band 10 with normal vision (floor is 15). So magnitude rides bar length in a single hue and identity rides the icon swatch + label. The two-series split pair clears at ΔE 20.7 deutan. Re-run the validator before substituting any chart color.
- **Auto-advancing content needs three guards**, all in `how-it-works.tsx`: a pause control (WCAG 2.2.2, for anything moving unprompted past 5s), a permanent stop once the reader picks a step, and `prefers-reduced-motion` meaning it never starts. Every slide's text stays in the HTML regardless — inactive ones are `aria-hidden`, so crawlers read all three and a screen reader reads one.
- **Live vendor counts were deliberately left out** of the hero. "1,200+ Colorado vendors" is a strong trust signal but makes `/` dynamic and DB-dependent, and reads "0" whenever the free-tier project is paused. If it's ever wanted, add it behind ISR with a null fallback, not a bare query.
- **`app/sitemap.ts` includes public vendor pages** (capped at 20k, `revalidate = 86400`) — those are the long-tail search asset, thousands of URLs with unique recon on them. It uses a plain `@supabase/supabase-js` anon client rather than `lib/supabase/server`'s, because reading cookies would force the route dynamic and there is no session to honour. Everything is wrapped in try/catch returning the three static routes, so a paused project or missing env can't fail the build.
- **`title` on the landing page uses `{ absolute: … }`** — the root layout's `"%s · Wedding Recon"` template would otherwise append the brand to a title that already opens with it.
- **No city/category landing pages** (`/denver-wedding-venues` etc.) — considered and rejected for now (Kiara, 2026-08-04). Generating ~100 pages that are each just a filtered map is the doorway-page pattern Google penalizes. Revisit once a city+category has enough recon to support real aggregate content ("median venue quote in Boulder"), which is content those pages would then legitimately have.
- Brand green is now tokenized: `--brand` / `--brand-ink` / `--brand-soft` in `globals.css` (exposed as `bg-brand`, `text-brand-ink`, …). Same three values the logo and category `venue` already used. Existing hardcoded `#1D9E75` usages (bottom-nav, brand-mark) still resolve to the same color and were left alone.
