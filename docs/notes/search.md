# Vendor search: one matcher, two bars

The shared `search_vendors` RPC behind the Explore bar and the Add Recon box, and how typo tolerance stays a second tier.

Moved out of `CLAUDE.md` (2026-09-12) to keep the always-loaded file small. Content is unchanged -- these are the as-built notes, so prefer them over re-deriving a rule from the code.

### Vendor search — one matcher, two bars (`lib/search/vendors.ts`)
- **Both search surfaces share one implementation.** The Explore bar (`/api/vendor-search`) and the Add Recon business box (`/api/places`) both call `searchVendors()` from `lib/search/vendors.ts`, which wraps the **`search_vendors` RPC**: token-AND over **name + `address_text` + `city`** (stop words dropped, every remaining token must appear — "the sanctuary" → "Sanctuary Golf Course"; stop-word list mirrored in `lib/search/tokens.ts`), then ranks by the **name-relevance scorer** that also lives there (`scoreVendorMatch`: exact > starts-with > word-boundary > contains > per-token, with a flat floor for rows that only matched address/city). **Change the matching or ranking rule in the RPC + that module and both bars move together** — don't reintroduce a per-route `ilike` chain or a second copy of the scorer.
- **Typo tolerance is a second tier, not a looser first one** (migrations `0026` + `0027`). Strict token-AND runs unchanged and, whenever it matches anything, is the whole answer — so no working query changes. Only when it finds **nothing** does a `pg_trgm` tier return up to 5 near-misses on **name** ("sanctaury" → "Sanctuary Golf Course"), every token needing to clear **`strict_word_similarity`** 0.35 (tokens under 4 chars must still match literally), ordered by the weakest token. **Use the `strict_` variant, not plain `word_similarity`** — the latter matches any trigram extent, including ones starting mid-word, which is how "sanctaury" pulled in "The Farmhouse Luxury Salon" at 0.400 ("…ury Sal…") next to real matches at 0.500. That junk isn't a weaker real match, so no threshold separates it; word-boundary extents drop it to 0.211 (`0027`). Those rows come back flagged `fuzzy` and scored **below every literal match** — a near-miss is a "did you mean", so it must never outrank what the user actually typed. Threshold and cap were tuned against real typo shapes vs. plausible-but-unknown business names; if you retune, keep the all-tokens-must-clear rule — it's what stops "mountain view lodge" matching "Spruce Mountain Ranch".
- What stays per-route is presentation only: row count, which fields render, `requireCoords` (Explore needs a pin to fly to, so coordinate-less vendors are dropped there and kept in Add Recon), and whether Google is blended in.
- `searchVendors` **never throws** — an unapplied migration or RPC error logs and yields no matches, so Explore still shows its Areas group and Add Recon still shows Google results.
- **Blended dedup (`/api/places`)**: searches Google Places autocomplete and our vendors **in parallel**, then merges. A Google prediction whose `place_id` matches an existing vendor is collapsed to the DB row (dedup — needs `google_place_id` from the RPC, added in `0024`). Existing rows are capped at 6 so a broad query can't crowd Google out of the 8 slots. Google predictions are scored with the same scorer (they carry no numeric score), which is what makes one ranked list possible.
- Returns a `SearchSuggestion` union: `{ kind: "existing", vendorId, vendorType, source, ... }` or `{ kind: "google", placeId, ... }`.
- Combobox (`components/add/places-combobox.tsx`) tags each row **"Google" / "User created" / "Featured"** (seed). Picking an existing vendor calls `onSelectExisting` → resolves straight to its `vendorId` (no new row, no Places details call) and **locks the type chip** (vendor type is canonical).
