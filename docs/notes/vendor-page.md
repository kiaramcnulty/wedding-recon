# Vendor page: caching, the media block, and the external-link overlay

How the page is cached and what is decided per viewer, the one photo strip, the short map, and how every outbound link is framed.

Moved out of `CLAUDE.md` (2026-09-12) to keep the always-loaded file small. Content is unchanged -- these are the as-built notes, so prefer them over re-deriving a rule from the code.

### External-link overlay (`<ExternalLink>`)
- All external links go through `components/external-link.tsx` — a real anchor (cmd/ctrl/middle-click keep native behavior) that intercepts a plain left-click to show the destination in a full-height overlay sheet (`components/external-overlay.tsx`, photo-lightbox portal pattern) with domain + open-in-new-tab + ✕ header and a sandboxed iframe (**no** `allow-top-navigation`, so framebusting scripts can't hijack the app tab).
- **Framing is the target site's choice** (X-Frame-Options / CSP `frame-ancestors`) and invisible to cross-origin JS, so embeddability is checked server-side: `embed={{ vendorId, kind }}` hits `/api/embed-check` in the background on mount (URL resolved from the vendors row — no raw-URL param, so no SSRF; failures → `false`; cached 1h browser / 24h CDN). Blocked or unchecked links behave exactly like `<a target="_blank">` — no dead-end taps.
- Static cases skip the check: **Instagram** profiles always block framing (`embed` omitted → plain new-tab link); **Google Maps** overlays the keyless iframe-embeddable view (`maps.google.com/maps?q=<name+address>&output=embed`) via `embedSrc` + `embed`. That endpoint is undocumented-but-ancient Google; if it ever dies, swap to the official (also free) Maps Embed API with a referrer-restricted key.
- **The iframe src is forced to https — an `http://` vendor site perma-loads otherwise** (`lib/embed-url.ts` `toEmbedSrc`, used by BOTH the overlay iframe and `/api/embed-check`). Reported 2026-08-15 as "Ramblin Express preview stuck on perma-loading, but it loads immediately if I open it externally". Root cause: the site is stored as `http://` and only serves https via a 301. The server-side `embed-check` **follows** that redirect and sees a frameable https 200, so the overlay opens — but the browser blocks the `http://` iframe as **mixed active content** *before* the redirect runs, so the frame's `load` event never fires and the spinner hangs forever. (A new-tab open is a top-level navigation, not a subresource, so it follows the redirect and works — which is the whole tell.) `toEmbedSrc` upgrades `http:`→`https:` so the frame loads the secure URL directly; the check probes the **same** upgraded URL so an http-only site (no working https) reports not-embeddable and falls back to a new-tab link (whose href stays the original http, correct for a top-level nav). **Only the iframe/check target is upgraded, never the anchor href.** This only manifests on the https production app — localhost dev is http, so an http iframe is same-scheme and won't reproduce it.
- **The overlay spinner has a 6s timeout** (`FRAME_LOAD_TIMEOUT_MS` in `external-overlay.tsx`): if `load` still hasn't fired, the spinner is replaced by an "Open in new tab" fallback for the residual cases the https upgrade can't catch (a downgrade-to-http redirect mid-load, a Safari-style no-load-on-block). It only swaps the spinner and is gated on `!loaded`, so a merely-slow site still resolves to the real page.

### Vendor page media block — one photo strip, short map
- **All photos live in ONE strip** (`components/vendor/vendor-photos.tsx`), recon photos first, then Google. It was two stacked strips — `GooglePhotoStrip` + `PhotoCarousel`, both now deleted — kept apart so community snaps never read as official marketing. They rendered identical tiles, so the split was invisible and just looked like two rows of the same thing: together with the map it filled the entire first screen (~558px) before any recon was reachable. Provenance is now per-tile, via an optional `badge` string on `LightboxPhoto` that paints a small "Google" chip; that is a clearer signal than a row break was, and it frees ~170px.
- **Google's attribution still has to show.** The caption reads `Google photos · <authors>` (not "Photos via Google") precisely because the strip now also holds photos that are not theirs — the per-tile chips are what tie the credit to the right tiles.
- **Measured, on a 390x844 phone:** the recon count now sits at y=438 and the first recon card is fully visible, against ~668px (below the fold) before. Tiles went 200x150 -> 150x112 and the map 176px -> 128px. If you add anything above the recon list, re-measure — getting the reader to the recon is the page's job (Kiara, 2026-08-04).
- **One strip also means one lightbox sequence** — opening any photo pages through all of them instead of stopping at the old row boundary.
- **Large, whole photos since 2026-11-28 (Kiara, after the preview cards got the same treatment).** Tiles are 240px tall and as wide as their photo at that height, so nothing is cropped: a 4:3 is 320x240, a portrait 180x240. With more than one photo a tile is capped at 90% of the strip (322px on a 390px phone), so a 4:3 still fits at full height and the next tile always peeks ~45px; a wider photo shrinks to the cap and sits centred, shorter than its neighbours. One photo may run the full strip width. The shape is read from the loaded image (`tileHeight` / `maxTileWidth` on `PhotoLightbox`; a ref catches photos that loaded before hydration), and an unloaded tile is a grey 4:3 placeholder, so lazy loading still keeps off-screen Google tiles off the network. The recon cards keep their fixed 80x60 cropped thumbnails.
  - **This reverses the 2026-08-04 fold measurement below on purpose.** Re-measured on a 390x844 phone: a venue (photos + map) now has its recon count at y=574 (was 438), with the first recon card starting in the first screen but not fully visible; a service-region vendor (no map) at y=381.
  - **Sharpness: a ~600px "medium" variant for uploaded photos (Kiara, 2026-11-28: "2x the data and still improves quality").** The 400px thumb is only ~1.25x density at this size, soft on a 3x screen; the 1600px full is ~10x the bytes. Measured on 200 bot photos: thumb 17.9 KB, medium (600px, q72) 35.6 KB = **2.0x**, full 183 KB. A 4:3 medium is ~1.9x density in a 320x240 tile, the same as the `w=600` Google tiles beside it (which are the preview cards' CDN key, so no extra billed fetch). Stored as `recon_media.medium_path` (migration `0053`) and as `medium_path` in listing photo jsonb; written by `lib/recon-upload.ts`, `lib/vendor-media-upload.ts` and the bot `upload.mjs` (made from the local full there, so old workdirs work). **Only the strip reads it**: the recon cards and the preview cards stay on the thumb, and a row without a medium falls back to the thumb, which is the state of every photo until `scripts/backfill-medium-photos.mjs` runs. Backfill cost is one full download per photo (egress) plus ~36 KB stored each; its dry run prints both.
- **Gotcha — a `snap-mandatory` strip needs `scroll-px-*` matching its `px-*`.** Otherwise the browser aligns the first tile to the container edge and scrolls the padding away, so the strip bleeds to the screen edge while the rest of the page keeps its gutter. Only visible once there are enough tiles to scroll, which is why it survived unnoticed in the old strips.

## URLs: `/vendor/<slug>` (2026-11-11)

Vendor pages live at `/vendor/<slug>` (`/vendor/dj-blnce`), generated by the database on insert (migration `0052`). Build every link with `vendorPath()` in `lib/vendors/slug.ts`; it falls back to the id when a caller has no slug in hand.

- **Slugs never change on their own.** The trigger is insert-only, so renaming a vendor keeps its URL. Collisions get the city, then a counter (`hampton-inn`, `hampton-inn-boulder`, `hampton-inn-boulder-2`), oldest row first.
- **Old uuid links still work, as a real 308.** `proxy.ts` -> `lib/vendors/legacy-redirect.ts` does one cookie-free lookup and redirects before any session work, keeping the query string (`from`, UTM). The page redirects too, but only as a fallback: `loading.tsx` streams the shell first, so a redirect thrown from the page arrives as a `<meta refresh>` with status 200 (the same reason a missing vendor is a 200 + noindex rather than a 404).
- **The recon query keys on the slug** through `vendor:vendors!inner(slug)` so it still runs in parallel with the vendor fetch instead of waiting for the id.
- **The map RPC is untouched.** Pins and list ordering stay id-based; the slug comes from the preview-card fetch (`useVendorPreviews`), which already selects each card's row by id.
- **Still on uuid links (they redirect):** the connector API (`lib/connectors/*`, its RPC `0049` is not applied yet), the `vendor-map.tsx` no-preview fallback, the recon-card edit fallback, and `scripts/cost-sheet`.

## Cached (ISR), with the per-viewer parts in the browser (2026-11-14)

`app/(app)/vendor/[id]/page.tsx` is ISR: `export const revalidate = 3600` plus a `generateStaticParams()` that returns `[]`. Nothing renders at build time; each vendor renders on its first visit and is then served from cache (Vercel's CDN) for everyone, crawlers included. `npm run build` lists it as `● /vendor/[id]` (it was `ƒ`). Why: a full render was ~37 ms of billed function CPU on every view (`docs/notes/function-cpu.md`).

**The render must read nothing per-request.** It uses `createPublicClient()` (`lib/supabase/public.ts`, cookie-free anon) instead of the cookie client, takes no `searchParams`, and makes no `cache: "no-store"` fetch (the Google photo refresh in `lib/google-photos.ts` used to, which would flip a photo-cache-miss render to dynamic). Any one of those turns the route back into a per-request render, and **nothing errors when it does** -- the build still shows `●`, because nothing is prerendered at build time. `scripts/test-vendor-page-static.mjs` (in `npm test`) guards those specific regressions. The real check is a second request: `x-nextjs-cache: HIT` locally, `x-vercel-cache: HIT` in production.

**What is decided in the browser** (Client Components; the cached HTML is the signed-out page):
- **Who is viewing**: `lib/viewer.ts`, a module-level store resolved once per document load (`getSession()`, a local cookie read; then, signed in, `profiles.is_admin` and the viewer's own non-removed entries, flagged ones included). `ViewerPreload` in the (app) layout starts it on whatever screen the visit begins on. These are display decisions only; every write re-checks identity server-side and RLS enforces it.
- **The recon cards** (`ReconCard` is now a Client Component): the green "yours" frame, the My recon · Edit pill, the admin-only Admin · Edit pill on bot recon, and the report flag they replace.
- **The slot above the list** (`components/vendor/recon-slot.tsx`): "Add recon", or **"Edit my recon"** for someone who already has recon here.
- **The `from` return path**: `BackButton` reads it from the address bar at tap time (no hook, so no Suspense). The Add/Edit links read it with `useVendorSelfHref()` (`useSearchParams`) under a Suspense boundary whose fallback is the same control pointing at the bare vendor path.

**Kiara's ruling (2026-11-14): public order for everyone, no shuffle.** A cached page cannot know the viewer, so "your own entry first" could only move after first paint. Instead: the list is in the same order for everyone, the viewer's card is marked where it falls, and the Add recon slot becomes "Edit my recon" in the same box (it used to disappear for people with recon, which would now move the whole list up ~56px after load). The pills were kept as they were rather than shrunk to a same-size icon. The "mine first" key left `sortReconEntries()` entirely, and the preview card stopped passing a viewer too, so a card still leads with the entry the page leads with.

**When a signed-in person sees their state:**
- **After an in-app tap** (Explore, the Hub, a back button): on first paint. The viewer is already resolved, so the cards and the slot render signed-in on their first render (checked: a DOM observer saw "Edit my recon" and the pill from the first insertion, never "Add recon").
- **On a cold load** (refresh, an opened link): the public page paints first and settles at hydration. The slot swaps its label in place (same 44px box, nothing moves); a pill can push its card's tags onto a second line, so that one card grows ~24px.
- **After signing out**: sign-out is a server action the browser client never hears about, so `ReconSlot` re-checks the session on mount; a soft navigation back to a vendor page draws the public state.

**Every app write that changes the page expires it** with `revalidateVendorPage()` (`lib/vendors/revalidate.ts`, one page by slug, never the whole route). `revalidatePath` without a profile EXPIRES in Next 16, so the next request renders fresh rather than being handed the old copy -- an author redirected back after saving reads their own write. Callers: recon create (`app/(app)/add/actions.ts`), recon edit, author or admin (`app/(app)/recon/[id]/edit/actions.ts`), report (`app/(app)/vendor/[id]/actions.ts`), verified listing save, vendor claim, claim revoke (`app/(portal)/portal/*`), and the Stripe subscription mirror (`lib/stripe/sync.ts`, shared by the webhook and the billing reconcile path).
- **Reports moved server-side.** The flag used to insert into `reports` from the browser. A second distinct report flips the entry to `flagged` (trigger in `0004`), which must take it off the cached page, and only server code can expire it, so `reportReconEntry()` does the insert and expires the page when the entry is no longer active.
- **Not covered, by design: writes that do not go through the app.** Seed and enrich uploads (bot recon), the reconcile writers, `filter-recon-daily`, a moderator editing a row in the Supabase dashboard, the background Google photo-ref refresh, and a subscription lapsing by date with no webhook. They show when the render ages out: after the hour, the next visit gets the old copy and triggers a fresh render (stale-while-revalidate), so allow up to an hour plus one visit.

**Other behavior that moved with it:**
- **A missing vendor is cached too** (the same 200 + `noindex` "Vendor not found" as before, for up to an hour). Create flows expire the new slug, so a vendor created after someone hit its URL still appears at once.
- **The page-level redirect is now query-less.** `proxy.ts` still 308s every `/vendor/<uuid>` URL with its query string kept, before the page runs; the page's own redirect (only reached if that lookup failed, or for a capitalized slug) cannot see the query string any more.
- **The query string does not split the cache**: `?from=...` and UTM tags hit the same entry.
- **`loading.tsx` stays.** It still covers a cache miss and the client navigation, and a cached document still carries it (the page content streams into place behind it).
- **Renders are deterministic** (two vendors rendered from the same data differ only in their own name, slug and id). That matters for cost: Vercel charges no ISR write when a regeneration produces the same output.

**How this was verified (2026-11-14), and what was not.** On a local production build against a stateful fake PostgREST + GoTrue (`/verify` skill), driven with headless Chrome over CDP: anonymous MISS then HIT with zero database reads; HTML, RSC and prefetch requests all HIT; the uuid 308; missing vendor; the Google-photo refresh path rendering and caching; and, with forged session cookies the fake backend accepts, the signed-in slot and pill, the flagged-own-entry case, the admin pill, the sign-out recheck, an author edit (back on the vendor page with the new price, anonymous HIT shows it), and two reports flagging an entry (next anonymous request MISS without it). **Not verified:** a real Supabase OTP session, the real RLS policies on the browser-side reads, and Vercel's CDN (`x-vercel-cache`) -- check those after deploy.
