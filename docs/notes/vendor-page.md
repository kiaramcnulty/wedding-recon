# Vendor page: the media block and the external-link overlay

The one photo strip, the short map, and how every outbound link is framed.

Moved out of `CLAUDE.md` (2026-09-12) to keep the always-loaded file small. Content is unchanged -- these are the as-built notes, so prefer them over re-deriving a rule from the code.

### External-link overlay (`<ExternalLink>`)
- All external links go through `components/external-link.tsx` — a real anchor (cmd/ctrl/middle-click keep native behavior) that intercepts a plain left-click to show the destination in a full-height overlay sheet (`components/external-overlay.tsx`, photo-lightbox portal pattern) with domain + open-in-new-tab + ✕ header and a sandboxed iframe (**no** `allow-top-navigation`, so framebusting scripts can't hijack the app tab).
- **Framing is the target site's choice** (X-Frame-Options / CSP `frame-ancestors`) and invisible to cross-origin JS, so embeddability is checked server-side: `embed={{ vendorId, kind }}` hits `/api/embed-check` in the background on mount (URL resolved from the vendors row — no raw-URL param, so no SSRF; failures → `false`; cached 1h browser / 24h CDN). Blocked or unchecked links behave exactly like `<a target="_blank">` — no dead-end taps.
- Static cases skip the check: **Instagram** profiles always block framing (`embed` omitted → plain new-tab link); **Google Maps** overlays the keyless iframe-embeddable view (`maps.google.com/maps?q=<name+address>&output=embed`) via `embedSrc` + `embed`. That endpoint is undocumented-but-ancient Google; if it ever dies, swap to the official (also free) Maps Embed API with a referrer-restricted key.
- **The iframe src is forced to https — an `http://` vendor site perma-loads otherwise** (`lib/embed-url.ts` `toEmbedSrc`, used by BOTH the overlay iframe and `/api/embed-check`). Reported 2026-08-15 as "Ramblin Express preview stuck on perma-loading, but it loads immediately if I open it externally". Root cause: the site is stored as `http://` and only serves https via a 301. The server-side `embed-check` **follows** that redirect and sees a frameable https 200, so the overlay opens — but the browser blocks the `http://` iframe as **mixed active content** *before* the redirect runs, so the frame's `load` event never fires and the spinner hangs forever. (A new-tab open is a top-level navigation, not a subresource, so it follows the redirect and works — which is the whole tell.) `toEmbedSrc` upgrades `http:`→`https:` so the frame loads the secure URL directly; the check probes the **same** upgraded URL so an http-only site (no working https) reports not-embeddable and falls back to a new-tab link (whose href stays the original http, correct for a top-level nav). **Only the iframe/check target is upgraded, never the anchor href.** This only manifests on the https production app — localhost dev is http, so an http iframe is same-scheme and won't reproduce it.
- **The overlay spinner has a 6s timeout** (`FRAME_LOAD_TIMEOUT_MS` in `external-overlay.tsx`): if `load` still hasn't fired, the spinner is replaced by an "Open in new tab" fallback for the residual cases the https upgrade can't catch (a downgrade-to-http redirect mid-load, a Safari-style no-load-on-block). It only swaps the spinner and is gated on `!loaded`, so a merely-slow site still resolves to the real page.

### Vendor page media block — one photo strip, short map
- **All photos live in ONE strip** (`components/vendor/vendor-photos.tsx`), recon photos first, then Google. It was two stacked strips — `GooglePhotoStrip` + `PhotoCarousel`, both now deleted — kept apart so community snaps never read as official marketing. They rendered identical tiles, so the split was invisible and just looked like two rows of the same thing: together with the map it filled the entire first screen (~558px) before any recon was reachable. Provenance is now per-tile, via an optional `badge` string on `LightboxPhoto` that paints a small "Google" chip; that is a clearer signal than a row break was, and it frees ~170px.
- **Google's attribution still has to show.** The caption reads `Google photos · <authors>` (not "Photos via Google") precisely because the strip now also holds photos that are not theirs — the per-tile chips are what tie the credit to the right tiles.
- **Measured, on a 390x844 phone:** the recon count now sits at y=438 and the first recon card is fully visible, against ~668px (below the fold) before. Tiles went 200x150 -> 150x112 and the map 176px -> 128px. If you add anything above the recon list, re-measure — getting the reader to the recon is the page's job (Kiara, 2026-08-04).
- **One strip also means one lightbox sequence** — opening any photo pages through all of them instead of stopping at the old row boundary.
- **Gotcha — a `snap-mandatory` strip needs `scroll-px-*` matching its `px-*`.** Otherwise the browser aligns the first tile to the container edge and scrolls the padding away, so the strip bleeds to the screen edge while the rest of the page keeps its gutter. Only visible once there are enough tiles to scroll, which is why it survived unnoticed in the old strips.
