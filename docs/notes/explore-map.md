# Explore map: pins, peek cards, feeds and list order

The map surface end to end -- what a pin looks like and why, what a tap does, when the vendor query fires, and the five keys that order every list.

Moved out of `CLAUDE.md` (2026-09-12) to keep the always-loaded file small. Content is unchanged -- these are the as-built notes, so prefer them over re-deriving a rule from the code.

### Service region drives two location signals
- **`usesServiceRegion(vendorType)` is the one switch** (`lib/constants/categories.ts`), backed by the `FIXED_LOCATION_TYPES` list: `venue`, `hotel`, `dress`. It already gated the recon form field and the `service_region` column; it now also drives the **map pin halo** and the **vendor-page map preview**. Add a type to that list and all four move together — never re-derive the test anywhere else. The rule is *does the couple go to them, or do they travel to the couple*: a bridal shop is a storefront you book an appointment at (`dress` moved here 2026-08-04, migration `0030`), while a florist has a shop but delivers and installs at the venue, so its travel radius is a real cost and it stays service-area. The enrich pipeline mirrors the same list as `serviceRegionRequired` in `etype.mjs` — keep the two in sync.
- **The halo is baked into the existing image ids, not a new variant axis.** Because it is a pure function of `vendor_type`, `lib/map/pin-images.ts` just draws `pin-flowers-solid` with a glow; `vendor-map.tsx` is untouched — no new layer, filter, source, or feature property. Service-area categories get bigger boxes (48/64/60 vs 36/52/48) to hold the glow; the disc radius is unchanged, and box size does not affect placement (`icon-allow-overlap` + `icon-ignore-placement`) or label offsets (ems of text-size), so nothing else moves.
- **The glow is deliberately edgeless**, a radial gradient that never resolves into a border. The other two pin signals are hard-edged and must stay separable at a glance: a **dashed** outline means "approximate address", a **crisp ring** means "this pin's card is open". Note ~10 of 12 categories are service-region, so on an unfiltered map the halo is closer to texture than to a badge — that is why peak alpha is low (`HALO_ALPHA`, the tuning knob). Inverting it (marking the two fixed-location types instead) is the obvious alternative if it ever reads as noise.
- **Gotcha — SVG gradient ids resolve per DOCUMENT.** Each rasterized pin is its own data-URI document, so a fixed `id="halo"` is safe there; but `vendorPinMarkup()` injects the same markup **inline** into the page, where a second pin sharing the id silently paints itself in the first one's color. Caught in review: a contact sheet of all categories rendered the blue Photos pin with the pink Flowers glow. Ids are namespaced `wr-halo-<type>-<box>`.
- **The glow is a separate unshadowed canvas layer.** `rasterize()` takes layers and applies the drop shadow per layer, because a blurred dark copy of a soft glow reads as grime. The disc keeps the exact shadow it always had, so haloed and un-haloed pins stay identical where they overlap.
- **The vendor page mirrors the split in one slot** (below the photos, above the recon): a fixed-location vendor gets `VendorMapPreview`, a service-region vendor gets its **service areas in words**, deduped from its recon entries' `service_region` (rendered only when that data exists — it explains the missing map rather than decorating the gap).
- **The mini-map is free.** MapLibre + the same OpenFreeMap tiles Explore uses — deliberately **not** Google Static Maps, which bills per image. It is `interactive: false` (a drag-to-pan map inside a scrolling column traps the touch gesture), and it initializes **on mount**, like `vendor-map.tsx`. The pin comes from the shared `vendorPinMarkup()` so it is pixel-identical to the one just tapped on Explore, dashed outline included.
- **Gotcha — never size a MapLibre container with `absolute inset-0`.** MapLibre stamps `.maplibregl-map` onto whatever element you hand it, and maplibre-gl.css declares that class `position: relative`. That is the SAME specificity as Tailwind's `absolute`, and the library stylesheet loads after Tailwind's utilities, so it wins: the container stops being positioned, `inset-0` no longer sizes it, and because every child MapLibre adds is itself absolute it collapses to **zero height**. Canvas, marker and attribution are all in the DOM and all invisible. Give the container an explicit `h-full w-full` inside a sized wrapper — which is why `vendor-map.tsx` never hit this.
  - This was the blank vendor-page preview reported 2026-08-04, and it cost two wrong fixes first. The diagnosis that worked was the **`verify` skill** (fake PostgREST + Playwright) probing the live DOM: `wrapSize 356x174` next to `innerSize 356x0` named the bug in one shot, after reasoning from screenshots had twice pointed at the wrong thing. Reach for it early on "renders but looks wrong" — a DOM probe beats inference. The symptom to recognise: **no attribution visible either**, since an AttributionControl inside a collapsed (or style-less) map renders empty, so missing credit means the map is broken rather than the tiles.
  - Init is gated on **`requestIdleCallback`, not on visibility** (2026-08-06). An IntersectionObserver gate was tried and removed while chasing the blank-preview bug above; it was not the cause, and it is still the wrong tool — on a 390x844 phone this map sits *inside* the first viewport, so a visibility gate fires immediately and saves nothing. But the note that replaced it ("the dynamic `import()` already keeps MapLibre in its own chunk, nearly all of the saving") was wrong on the part that matters: a separate chunk keeps MapLibre out of the *initial bundle*, yet a mount-time effect downloads and executes it immediately anyway, so it lands in the initial load regardless. **Measured** on the built app: a venue page went 529 KB / 40 requests before this preview existed to 850 KB / 45 after — +1.2 MB decoded JS, a ~466 KB MapLibre worker blob, and a basemap fetch to `tiles.openfreemap.org` (a third-party origin, so a fresh DNS + TLS handshake before the style/sprite/glyph/tile fan-out even begins), all racing hydration and the photo strip. Scheduling is the right axis: the map is an orienting glance, not the content. `requestIdleCallback`'s **`timeout` is load-bearing** — it guarantees the callback runs, which is precisely what the observer could not promise, so the permanently-grey-box failure cannot recur; browsers without it (Safari < 16.4) fall back to a short `setTimeout`. Measured after: page chunks finish at +358 ms, the map starts at +568 ms. Note this **reorders** work, it does not remove bytes — the payload is inherent to putting a WebGL map on the page, so if vendor-page weight is the problem, the lever is gating the map behind a tap, not tuning the delay.
  - Two guards came out of it: `map.resize()` on load (MapLibre measures its container once at construction and never watches it), and an `error` handler that logs, since a failed style is otherwise completely silent.
  - The compact AttributionControl starts **expanded** (`maplibregl-compact-show`), which costs 44px of a 174px preview; the `load` handler removes that class so it collapses to the "i". Credit stays one tap away, which is what the compact affordance is for — remove the class rather than overriding the CSS, or the toggle stops working.
- **The "View larger map" chip is TOP-right on purpose.** MapLibre's compact attribution collapses to an "i" only on a narrow map and expands to a full-width credit bar on a wide one, which landed straight on top of a bottom-right chip on desktop. Basemap attribution is required by OpenFreeMap/OSM, so it also has to stay clickable: the tap overlay is `z-[1]` and the control corner is lifted with `[&_.maplibregl-ctrl-bottom-right]:z-[2]`.

### Approximate-location map pins
- `isApproximateLocation(vendor)` heuristic: **non-Google source + no digit in the address** ⇒ approximate (geocoded to a city/region centroid, not a street address). Known blind spot: numbered street names ("E 17th Ave") read as precise. The robust replacement is to **store geocode precision at save time** (Nominatim returns `addresstype` + a `boundingbox`) and key off that field instead.
- Approximate pins get a **dashed** white outline (vs solid); pins sharing a rounded coordinate are **fanned out** across a compact phyllotaxis disc (`~110m·√n`, deterministic by vendor id so they don't jump on pan). Both live entirely in `vendor-map.tsx` — no migration, since the RPC already returns `source`/`google_place_id`/`address_text`.
- For very large piles (~50) the fan-out only fully separates at city zoom; if that becomes common, add a click-to-list drawer (discussed, not built).

### Pin labels + the single-pin peek card (Zillow pattern)
- **One preview card, FOUR surfaces.** `components/map/vendor-preview-card.tsx` owns both the card (photo → category pill → name → **"City, ST" locality** → recon count, plus the swipeable recon-text carousel) **and** its data fetch (`useVendorPreviews(ids)`). The cluster feed, the on-screen results feed, the single-pin peek (`vendor-pin-preview.tsx`), **and the Planning Hub** (`hub-accordion.tsx`) all render it — change the card there and every surface moves together. Don't re-inline a second copy. The card's main control is a **`<Link href>`, not a button calling `router.push`** — that is what gets `/vendor/[id]`'s `loading.tsx` prefetched, and without it Next does not know the route has a loading boundary until the whole RSC response lands, so a tap sits there doing visibly nothing. Measured in the results feed with card photos still in flight: **821ms tap-to-navigation as a button, 241ms as a Link**. It reported as "I cannot click the card until its photo loads" (Kiara, 2026-08-04) — the click was in fact registering within ~45ms; the photos were simply competing for bandwidth with the un-prefetched navigation, so the two finished together. Same lesson as `/recon/[id]/edit`. Surfaces pass `href` plus an optional `onNavigate` for side effects (the feed saves its scroll position there); the recon carousel below the link still navigates via `router.push`, since a horizontally scrollable strip cannot live inside an anchor. **The link needs `no-underline!`** — in the Hub it sits inside `AccordionContent`, whose `[&_a]:underline` out-specifies a plain utility. Two props flex it per surface instead of forking it: **`showCategoryPill`** (off in the Hub, where cards already sit inside a category accordion) and **`action`** (a trailing control — the Hub's "Add" button — rendered as a **sibling** of the main button, never nested inside it). `useVendorPreviews` also resolves the viewer via `getClaims()` so **their own recon sorts first in the carousel and is tagged "My recon"**, matching how the vendor page orders its entry list (the shared comparator — see "Recon entry order within a vendor" below); Explore is public, so a null viewer is normal and the "mine first" key and the tag are simply no-ops.
- **The feed pages 20 at a time, and `useVendorPreviews` caches by id.** Reported as "list view takes 5-10 seconds, especially past 20 vendors, but only sometimes" (Kiara, 2026-08-06). The feed was handed up to `MAX_VISIBLE_ENTRIES` (200) rows and asked for previews of all of them at once — and the preview fetch pulls **every active recon entry for every id**, full `notes`/`price_details`/`price_text` prose plus a `recon_media` join, to render a two-line truncated carousel. Measured against a realistic corpus at 119 vendors: **237 recon rows, 171 KB, on a request URL of 4,770 characters** (200 ids is ~8 KB, at or past what gateways will carry — which is the likeliest source of the intermittency, since the URL grows with how many pins are in view). `VendorFeed` now renders `entries.slice(0, shownCount)` and grows by `FEED_PAGE_SIZE` from an IntersectionObserver sentinel with 600px of runway. Throttled 4x-CPU/1.6 Mbps: **1352ms -> 423ms to first cards**, with the page query at 40 rows / 29 KB on a 998-char URL.
- **Note what was NOT the problem: rendering.** The feed already had `content-visibility:auto` + `contain-intrinsic-size` per row and `loading="lazy"` on card images, so off-screen cards cost nothing to paint. Paginating the DOM would have bought nothing; the fix is windowing the **query**. Check which one you are actually paying for before adding virtualization.
- **`useVendorPreviews` must never blank on a growing list.** It used to `setItems(null)` at the top of its effect, so any id-set change dropped the whole feed to a spinner — including paging in more rows, which would have made windowing worse than the disease. It now keeps a `Map<id, VendorPreview>` and fetches **only ids it has never seen**, returning null solely when it has nothing at all. The split matters: the cache is **state** (the render reads it, and a ref cannot be read during render) while the seen-set is a **ref** (the effect reads it, and depending on the cache it just wrote would loop). Ids are marked seen when *requested*, not when returned, so a deleted vendor is not re-requested forever. Cache is dropped wholesale past `PREVIEW_CACHE_MAX`.
- **Two React rules bite here and both have a right answer that is not a suppression.** Resetting the window when the entry list changes is done by **setting state during render** (React's documented "adjust state when a prop changes"), not in an effect — an effect sets it after paint, so the couple sees a frame of the previous list, and it trips `react-hooks/set-state-in-effect`. And the derived list is a `useMemo` over **state**, because `react-hooks/refs` correctly rejects reading `ref.current` during render.
- **The card's locality subtitle comes from `formatVendorLocality()`** (`lib/vendor-locality.ts`), shown for **every** vendor type. `city` + `region` are the source of truth; `address_text` is parsed only to fill a gap, scanning from the END and accepting a state **only in the last two comma segments** — without that guard a street name carrying a state abbreviation ("Mt Vernon Rd" → MT) hijacks the parse and drags a junk city along. A bare state with no city renders as nothing, since "CO" alone reads as a data glitch. `normalizeRegion()` doubles as the is-this-a-state test: it returns unmapped input unchanged, so *requiring a clean 2-letter result* is what makes it reliable. The Hub's loading skeleton renders the locality too (it has the vendor row server-side already), so cards don't gain a line when previews land.
- **One list sheet, two feeds.** `components/map/vendor-list-sheet.tsx` is the bottom-sheet feed itself (portal, backdrop, scroll lock, swipe-down, scroll restore). It takes `entries: {id, vendorType, rank?}[]` — **a type per row**, so a feed can mix categories — plus a `heading` and the `scrollKey` its scroll position parks under. `cluster-list-sheet.tsx` is a thin wrapper over it; the results feed passes mixed rows straight through. **Both feeds arrive pre-sorted by the map**, via the shared `compareRanked` — see "List view order".
- **A pin tap peeks, it doesn't navigate.** `VendorMap` calls `onVendorOpen` and Explore floats the card over the bottom of the map; tapping the *card* is what opens `/vendor/[id]`. The peek is deliberately **not** a modal — no portal, no backdrop, no scroll lock — so the map stays pannable and the next pin tap just swaps the card. Dismissed by the ✕, Escape, a swipe down, or a tap on empty map (`onBackgroundTap`, which fires when `queryRenderedFeatures` hits no pin/cluster layer). With no `onVendorOpen` wired up, a pin tap falls back to navigating straight to the vendor page.
- **Names on pins from zoom `LABEL_MIN_ZOOM` (= 12).** It's a standalone constant, deliberately *below* `CLUSTER_MAX_ZOOM` (14) so names appear earlier on the way in — it used to be `CLUSTER_MAX_ZOOM + 1` on the reasoning that cluster bubbles must be gone first, but that was never the thing making a label unambiguous: the pin layer is filtered to unclustered points, so a labelled feature is a single vendor at any zoom. Labelling below the cluster ceiling just means the names you get are the isolated pins between bubbles, with the crowded ones collide-dropping. Still at/below the zoom a vendor search flies to, so a searched pin arrives named. Labels are `text-field` on the existing pin layers (no new layer): `["step", ["zoom"], …]` with the zoom test at the **outermost** level, which is what lets a layout property mix zoom with a per-feature `["get","name"]`. `text-optional` + no-overlap means crowded labels **collide-drop** while the pin always renders (the icon ignores placement entirely).
- **The selected pin** (the one whose card is open) swaps to an **emphasized pin image** — a bigger disc inside a category-colored ring, `pinImageId(type, approximate, true)` in `pin-images.ts`, rasterized alongside the plain ones at load — and gets a larger name label at *any* zoom. All of it is layout expressions on the existing pin layers (`selectionLayout()` + `applySelection()`, same shape as `applyTypeFilter()`), keyed off an `iconSelected` feature property, so a selection change is four `setLayoutProperty` calls per type with no new layers or sources. A plain scale-up was tried first and wasn't readable enough next to its neighbours.
- The peek card renders **above** the brand-mark/locate control row (both inside one `mt-auto` bottom stack), so opening it doesn't push those controls up and out of reach. A pin tapped inside the bottom `PREVIEW_SAFE_PX` (300px — card + that row + the attribution gap) is **panned up** so the card never covers the pin it describes.
- **Restore-on-return** mirrors the cluster sheet: `wr:pin` in sessionStorage + `?from=/explore?restore=1`. The two are mutually exclusive (opening one clears the other's key). The URL marker is consumed **inside** the deferred `setState`, not before it — in dev React mounts twice and the first pass's cleanup cancels that timeout, so dropping the marker up front left the second pass with nothing to restore.
- **Every overlay over the map opts IN to pointer events; nothing inherits them.** The whole over-the-map stack sits in one `pointer-events-none absolute inset-0` box (added when the list view needed a bounded height), so a control that does not carry `pointer-events-auto` is inert — the tap goes straight through to the MapLibre canvas. That silently broke the entire top bar (brand mark, search bar, profile menu) and the bottom stack (pin peek card, locate button); the two rows that were written after the wrapper had it, the two that predated it did not (fixed 2026-08-06). Put `pointer-events-auto` on the **individual controls**, never on the row: each row is a full-width band, and the gaps between controls have to stay pannable map. That is also what retired the old "the bottom row eats every map tap in its ~90px band" note — the row is click-through now and only the button itself takes taps.
  - **Nothing fails loudly**: the control renders, hovers, and looks correct; it just does not respond. The one-line check is `document.elementFromPoint(x, y)` at a control's centre — if it returns `canvas.maplibregl-canvas`, that control is dead. Playwright's own hit-target check catches it too (`page.click` times out rather than clicking through).

### Explore's fetch does not wait for the map
- **The vendor query starts at MOUNT, before MapLibre is even downloaded.** It used to live inside `map.on("load")`, which put it at the end of a chain it had no real dependency on: download the ~1 MB MapLibre chunk, construct the map, fetch the basemap style from `tiles.openfreemap.org`, parse it, fire `load`, *then* ask Supabase for pins. Measured on a 4x-CPU / 1.6 Mbps / 150 ms profile, the style request had not even **started** until +5.9 s — the pins were queued behind a third-party CDN for nothing. After the change the query fires at **+2.9 s**, about 4.3 s before the style request, and the map still only issues **one** `vendors_in_bbox` on load.
- **What made it possible is that a bbox is a pure function of center, zoom and container size**, all known at mount — so `lib/map/viewport.ts` computes it (Web Mercator, 512 px tiles, matching MapLibre's transform) instead of asking `map.getBounds()`. `fetchVendors()` was split into `fetchBbox(box)` (explicit box, no map needed) and the map-reading wrapper.
- **The prefetch result is not plumbed into the load handler — it is handed over through `coverageRef`.** `fetchBbox` records the box it fetched as covered, so the `fetchVendors()` call inside `load` sees an ordinary cache hit, returns null, and the handler applies the prefetched rows. That is why there is no second query and no new synchronisation to reason about: it reuses the pan cache that already existed. If the container has not been laid out, `bboxForView` returns null and it falls back to the old fetch-after-load path.
- **The remaining floor is hydration, not the map.** +2.9 s is when React can first run an effect on a throttled phone. Going below that means server-rendering the initial rows into the page, which is a different (bigger) change.
- **`filters` is fetched lazily and merged in** (migration `0034`). `withFilters` latches true when the filter sheet is first opened — not on the first chip tap, so the fetch overlaps the couple reading the sheet — and from then on later pans fetch pins and attributes together. Before they land every vendor ranks 1 (unfiltered), so the transient is "nothing has dimmed yet", never a wrong answer. Verified end to end: initial load 1 vendors / 0 filters, sheet open 0 / 1, pan off coverage 1 / 1.

### "See all N results on screen" (the results pill)
- **The count is computed in the map, not the page.** `vendor-map.tsx` keeps the last applied rows + their resolved display positions in refs and answers "what's on screen" against `map.getBounds()` on every settled move, after new rows land, and on a type-filter change — emitting `{ total, entries }` via `onVisibleVendorsChange`. It's deliberately **not** `queryRenderedFeatures`, which answers "what's rasterized": that collapses clusters into one feature and misses pins outside the painted tiles. Positions come from the same fan-out resolver the pins use, so the count matches what's drawn.
- **Recount on `moveend` is immediate**, not on the debounced refetch — the pill has to track the viewport. It's pure in-memory work over rows already held, and a pan that changes nothing emits nothing (the payload is diffed by an id key), so no re-render churn.
- **The filter is respected for free** — the same `selectedTypes` that toggles layer visibility gates the count, so multi-type selections just sum. The feed mixes those types in one list; `screenListHeading` only names a category when the list is unambiguously one type (user filtered to exactly one, or a complete list happens to be homogeneous).
- **Capped at `MAX_VISIBLE_ENTRIES` (200) rows, nearest the map center first** — `useVendorPreviews` puts every id in one PostgREST `in.()` filter, and a few thousand uuids would blow the URL limit. `total` is always the true count (the pill must not lie); when the list is capped the sheet says so in a footnote. If a deeper list is ever wanted, paginate the feed rather than raising the cap.
- **The open list is a frozen snapshot** (`wr:screen` in sessionStorage, scroll under `wr:screenScroll`), for the same reason the cluster feed is: the sheet is modal, and a list reshuffling under a scroll would be unusable. It's mutually exclusive with the cluster sheet and the pin peek — opening any one clears the other two keys.

### List view order
- **Five keys, in `compareRanked()` in `vendor-map.tsx`** — `rank`, then `matched`, then `priced`, then `photo`, then distance from the map center. **BOTH feeds use it**: the on-screen results list (`reportVisibleVendors`) and the tapped-cluster sheet. The cluster sheet used to render `getClusterLeaves()` order, which is supercluster **tree** order — spatial-index insertion order, arbitrary to a reader — so the same two vendors came out differently depending on which way the list was opened (reported 2026-08-07: a "No quote found" photographer above one quoting $2.5k). The scoring is `rankVendor()`; a sixth key goes in those two functions and both feeds move together. Each only reorders within the tier above it, so distance still decides at the bottom. The same comparator serves the unfiltered list and the filtered one; with no filter active every row is rank 1 with `matched` 1 and both keys simply drop out.
- **The partial tier is itself graded, by `matched`** — a vendor silent on 1 filter of 3 outranks one silent on 2, and within each of those bands the priced/photo/distance keys apply exactly as they do above the divider. Only silences count: a contradiction is rank −1 and never reaches the list at all.
- **A rank-0 pin recedes hard on the map** — `PARTIAL_ICON_OPACITY` 0.22 / `PARTIAL_LABEL_OPACITY` 0.28 in `vendor-map.tsx` (was 0.45/0.55; dropped 2026-08-06 now that silence no longer excludes and the faded population is much larger). Measured on a render, the partial disc sits at 22% of a full-match pin's colour saturation against 45% before. The label goes fainter than the disc because text at low opacity fades its white halo too, so it stops being legible while still adding clutter. **The old "keep it above 0.4 so it still looks tappable" floor is deliberately gone** — tapping is unaffected (MapLibre hit-testing ignores opacity), and the compensation is the selection override below. If a pin ever reads as invisible on a dark basemap feature (a park, say), these two constants are the knob.
- **The SELECTED pin is always fully opaque, whatever its rank** — `selectionPaint()`, applied by `applySelection` alongside the layout pass. Opacity is a **paint** property while everything else about selection is **layout**, so it needs its own `setPaintProperty` loop; miss that and tapping a faded pin opens a card next to a ghost.
- **Silence NEVER excludes — there is no exception** (changed 2026-08-06). `rare` filters used to invert the rule, dropping silent vendors on the reasoning that a hotel running a shuttle would say so. That was quietly deleting most of the map on one tap (filtering photographers on "also shoots film" ruled out **233 of 274**; it is now 3 ruled out — the ones saying an explicit `false` — and 230 demoted), and it was wrong in exactly the case it meant to catch, since a vendor is silent far more often because nobody extracted the fact than because they lack the thing. `rare` is now a **UI badge only** ("Rare" in the filter sheet, warning that a filter will not narrow much); the matcher does not read it, and `buildSelection` no longer stamps it onto a spec. Consequence to expect: those filters now leave a large dimmed-pin population on the map and a long partial tier in the list, which is the honest picture.
- **`matched` is a FRACTION, not a count of misses**, and the two are not interchangeable. A mixed-type search is one query, so a venue judged on 3 attributes and a photographer judged on 2 both being "silent on 1" is 67% against 50% — and the feed interleaves them. With a single type filtered (the common case) the two orderings are identical, since every vendor shares the denominator. `matchedFraction()` in `lib/filters/match.ts`.
- **It sits at key 2 rather than being special-cased to rank 0** because it is already a no-op above the divider: a rank-1 row matched everything, so it scores 1, as does a row whose type carries no filters at all.
- **`filterMatch` / `filterMatchFor` are the counting form of `filterRank` / `filterRankFor`**, returning `{ rank, unknown, active }`; the rank functions are now thin wrappers, so there is still one implementation of the rules. `unknown` rises by at most 1 per filter — every branch that notices a silence also ends that filter's turn — so it can never exceed `active`. `scripts/test-filter-match.mjs` covers the arithmetic; it is the only executable check on the matching rules, so run it after touching that module.
- **`rank` is the only tier with a visible divider** — `"Partial matches in the area"`, drawn in `vendor-feed.tsx` where the list crosses from full matches (rank 1) to the ones a filter could not confirm (rank 0). Matched, priced and photo are **internal**: they rank vendors that all equally match what the couple asked for, so a break there would imply a distinction the couple never drew. A partial match is different in kind, and saying so is what stops those rows reading as matches. Rank −1 rows are excluded outright and never reach the feed.
- **The divider is derived from the RENDERED items, not from `entries`.** `useVendorPreviews` silently drops ids whose vendor row is gone; anchoring on `entries` means such a row can take the divider with it and leave everything below it reading as a full match. It is also drawn when it lands at the very top (every result partial) — odd as a "divider", but far better than presenting rows that match nothing as though they did.
- **`has_price` and `has_photo` are computed in SQL** (`0035`), for the same reason `approximate` is: the sort runs over the whole viewport **before** the feed pages 20 at a time, so the flags cannot come from the per-card fetch, which only ever sees the page already chosen. Two booleans is ~2 B/row against the 208 B/row `0034` measured.
- **The pricing tag is `vendors.filters`** — any **numeric** key whose name contains `price`. That is what makes it generalize across types without naming them (`price_min`, but also `bride_price_min` / `party_price_max` / `trial_price` for hair & makeup); a verbatim `price_quote` with no parsed number counts too. Deliberately **not** the string keys `price_basis` / `price_kind` / `price_confidence` — those describe a price rather than being one. Measured on the 2,163-row corpus: **818 (37.8%)**, a real split rather than a near-empty tier. **Hotels model no price at all** (the type has `block_type` and `min_rooms`, never a rate), so every hotel sits in the unpriced tier permanently; inside a category-filtered view they all tie and the sort falls through.
- **`has_photo` must NOT test `google_photos` strictly.** That column is a **lazy cache** filled on the first view of a vendor page (`lib/google-photos.ts`), so a null means nobody has looked yet — never that the vendor has no photos. Testing it strictly ranks vendors by whether somebody happened to open them, which is view history, not a fact. The SQL mirrors what `photoCandidates` in `vendor-preview-card.tsx` actually does: a non-empty array, **or** null-with-a-`google_place_id` (optimistic, the common case), **or** any active recon photo. An empty array is the one negative — resolved, and Google had nothing.
- **Both flags need `coalesce(…, false)`, and it is load-bearing.** They are OR chains over jsonb tests, and a jsonb test on a missing key yields NULL, so `false OR NULL` is NULL: without it the columns come back **NULL on exactly the rows that mean no**, and a later `not has_price` would match nothing. Found by running the migration, not by reading it. The client compares `=== true` for the same reason — that also makes a missing column (pre-`0035`) read as false for all rows alike, so both keys become no-ops and the order falls back to nearest-first rather than being corrupted by `NaN`.
- **The recon-photo `EXISTS` sits LAST in its OR on purpose.** The two cheap column tests are true for almost every seeded vendor and an OR stops at the first true, so the semi-join is skipped on the common path. Verified with `explain analyze`: **5 loops over 2,178 rows**, rising to exactly 305 once 300 rows were stripped of their `google_place_id`.

### The partial tier has to show up on EVERY counting surface
- Reported as "the filter says only 5 matches but the map and list show far more" (Kiara, 2026-08-06). Nothing was miscounted: the sheet footer said `5 matches on screen · 121 missing some info`, the pill said `126 results`, and 5 + 121 = 126. **Because silence never excludes, the partial tier is usually the majority of what is on screen** — 382 of 679 CO venues carry no price at all — so any surface printing a bare count of "what is showing" is printing that tier, not the answer. The pin fade and the feed divider were already doing the right thing; three other surfaces were not. **When you touch the matcher, walk every surface that renders a count or a list.**
- **Cluster bubbles count matches**, via a supercluster `clusterProperties: { matched: ["+", ["get","rank"]] }` on each per-type source (`rank` is 1/0 per point, so summing it counts matches). This was the surface that made the report so stark: at the zoom in the screenshot there are **no individual pins at all**, only bubbles, so the one signal that existed was invisible. The label is a three-way `case` — all leaves matched → `point_count_abbreviated` (so the unfiltered case is byte-for-byte what it always was, `1.2k` included), some matched → the match count, none matched → the abbreviated total, receded to the same `PARTIAL_ICON_OPACITY`/`PARTIAL_LABEL_OPACITY` an individual rank-0 pin gets. Free to keep current: a filter change already rebuilds the source through `applyVendors`.
- **The pill reads `N of M`, not `M results`**, and the full sentence lives in its `aria-label` — the chip shares a 390px row with the filter button and the view toggle, so anything longer truncates away exactly the number that was added.
- **A cluster tap passes `{id, rank}[]`, not `string[]`** (`ClusterOpenPayload.entries`), which is what lets the cluster feed draw the divider `VendorFeed` already knows how to render — it was handing over bare ids, so every row read as a full match. Its heading counts matches too. The `wr:cluster` sessionStorage payload changed shape with it, and the restore path still accepts the old bare-`ids` form as all-matches.
- **`basisScale` makes a stated assumption real.** `VENUE_PRICE_ASSUMPTIONS` (100 guests, 5 hours) was rendered in the sheet's footnote and used by **nothing**: the histogram binned a $150-per-person venue raw into the $0-499 bar while the matcher demoted that same venue for being silent on a price it had published. A `FilterDef.basisScale` map now converts a convertible off-basis quote in **both** readers, and a basis with no factor (`per_night` on a venue, or a caterer's per-person against a package slider) still reads as silence. Scaling goes **after** the season/day tier lookup (a tier is quoted in the vendor's own basis) and **before** the open-ended `OPEN_HI` sentinel, which is not a price and must never be multiplied.
