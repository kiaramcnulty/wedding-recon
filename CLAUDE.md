# Wedding Recon

Mobile-first PWA for engaged couples to (1) explore local wedding vendors on a map and (2) log + save their own "recon" (price quotes, notes, photos) in a personal planning hub. Non-revenue — favor free/low-cost choices. Soft-launch market: Denver, CO.

Full product/dev plan: see the approved plan referenced in the repo history; this file is the working reference for conventions.

## Stack
- Next.js 16 (App Router, TypeScript, Turbopack) — see `AGENTS.md`: this Next is newer than your training data, check `node_modules/next/dist/docs/` when unsure.
- Tailwind v4 (CSS-based config in `app/globals.css`, no `tailwind.config.js`).
- shadcn/ui components in `components/ui/` — these wrap **Base UI** (`@base-ui/react`), not Radix. Follow the existing component files for APIs.
- Icons: `lucide-react`.
- Supabase (Postgres + PostGIS + Auth + Storage + RLS).
- Map: MapLibre GL JS + free OpenFreeMap tiles. Google Places only for business search in Add Recon.

## Conventions & contracts (do not break these)
- **Vendor categories**: import from `lib/constants/categories.ts` (`VENDOR_TYPES`, `CATEGORIES`, `RECON_TYPES`, labels). Each type has a fixed icon + color reused on pins, chips, accordions, tags. Never hardcode category colors elsewhere. **Music was split into two types — `dj` ("DJs") and `band` ("Live music", the broad live-performer bucket: bands, quartets, soloists, pianists, ceremony ensembles). `music` is now a hidden legacy value (`LEGACY_VENDOR_TYPES`), kept in the enum + `CATEGORIES` only so a straggler row still renders.** **`beauty` ("Hair & makeup", Sparkles icon, teal — migration `0022`) is ONE joint type for wedding-day hair AND makeup: most artists do both, and a hair-only or makeup-only artist goes in the same bucket rather than a second category.** **`hotel` ("Hotel blocks", Hotel icon, navy — migration `0023`) is guest-lodging ROOM BLOCKS, not event space: **venue supersedes hotel** — a property with a ballroom/ceremony site is normally a `venue` even when it also blocks rooms, and `hotel` is for stay-only properties. **EXCEPTION (Kiara, 2026-08-03): where a property is primarily valuable to couples AS A ROOM BLOCK, type it `hotel` even if it has event space** — judged per property, because the listing should lead with what couples actually come to it for. The Maven Hotel and Holiday Inn Estes Park were re-typed `venue` → `hotel` under this rule: both are repeatedly recommended on Reddit for guest blocks (Maven at ~$250/night against a $450 rack rate), and Holiday Inn Estes Park's own recon says it is "not marketed as a wedding venue". A second row is NOT an option — `vendors.google_place_id` is `unique`, so one property is one row and the block-vs-venue call is a typing decision, not a duplication one. That rule is self-enforcing at seed time — `upload.mjs` dedups `google_place_id` GLOBALLY across types, so a property already seeded as a venue is skipped rather than re-inserted.** Use `VENDOR_TYPES` for anything user-selectable (picker, Explore filter, Hub); `ALL_VENDOR_TYPES` to validate a value that might be legacy.
- **Types**: shared row types in `lib/types.ts`.
- **Supabase clients**:
  - Client Components → `createClient()` from `lib/supabase/client.ts`.
  - Server Components / Route Handlers / Server Actions → `await createClient()` from `lib/supabase/server.ts`.
  - Service role (server-only, bypasses RLS) → `createServiceRoleClient()` — use sparingly.
- **Auth session** is refreshed in `proxy.ts` (Next 16's renamed middleware). Don't gate public vendor pages — shared deeplinks must render without an account.
- **Map geo query**: call the `vendors_in_bbox` RPC; it returns flattened `lng`/`lat` plus a precomputed `approximate` boolean for pin styling. Migration `0034` cut it to exactly what draws a pin (id, name, type, lng, lat, approximate — about 208 B/row against 625 B before): `filters` moved to its own `vendor_filters_in_bbox` RPC, fetched only once the filter sheet is opened, and `source`/`google_place_id`/`address_text` went away because the only thing reading them was the approximate-location heuristic, which is now a boolean computed in SQL. Both shapes are handled by the client, so applying `0034` needs no coordinated deploy — see "Explore's fetch does not wait for the map" below. Migration `0035` adds two more server-computed booleans, `has_price` and `has_photo`, which the list view sorts on — see "List view order" below.
- **Map markers**: `components/map/vendor-map.tsx` gives approximate-location pins a dashed outline and fans out pins that share a coordinate (deterministic phyllotaxis). See "Approximate-location map pins" below. Individual pins carry the **vendor name** from zoom 15 up, and a pin tap opens a **peek card** over the bottom of the map rather than navigating — see "Pin labels + the single-pin peek card" below. **Service-region categories additionally get a soft radial "flashlight" glow** — see "Service region drives two location signals" below.
- **Schema** lives in `supabase/migrations/`. If you change the DB, add a new numbered migration — don't edit applied ones. Write them idempotent and **apply new ones by hand in the Supabase SQL editor** (not auto-applied to the hosted DB). See "Migrations" below.
- **Copy/nomenclature**: the recon CTA is **"Save recon"** (not "Publish"); user-facing labels say **"Vendor"**, not "Business".
- **External links**: use `<ExternalLink>` from `components/external-link.tsx`, never a bare `<a target="_blank">`. It shows the destination in an in-app overlay sheet when the site allows framing, and degrades to a plain new-tab link when it doesn't. See "External-link overlay" below.

## App structure
- `app/page.tsx` — the **marketing landing page** at `/` (statically prerendered, desktop-first, no bottom nav). It used to be a bare `redirect("/explore")`; the redirect now lives in the middleware and is conditional. See "Landing page + first-visit routing" below.
- `app/(app)/` — main screens with the mobile frame + bottom nav: `explore`, `add`, `hub`, and `vendor/[id]`.
- `app/(auth)/` — login / onboarding (no bottom nav).
- `components/` — shared components (`bottom-nav.tsx`, plus feature components).
- `components/landing/` + `lib/landing/` — landing-page-only components and content. Nothing under `app/(app)/` should import from them except the two links back (`BrandFooter`, `ProfileMenu`), which take `LANDING_HREF` from `lib/landing/nav.ts`.
- Mobile frame is `max-w-[480px]`, centered. The landing page is the one screen that is **not** in that frame — it runs to `max-w-5xl`, since it is the only surface people meet on a laptop.

## Key patterns & learnings

### Landing page + first-visit routing
- **`/` serves two different things, and the middleware decides which.** A first-time visitor gets the marketing page; anyone who has already reached the product — or is signed in — is redirected to `/explore`. The whole rule is `applyFirstVisitGate()` in `lib/landing/first-visit.ts`, called from `proxy.ts` after `updateSession()`. Constants (cookie name, the `?ref=app` marker, `isProductPath`) live in `lib/landing/nav.ts`, which is deliberately free of `next/server` imports so a Client Component can import `LANDING_HREF` without pulling the server runtime into its bundle.
- **The gate belongs in the middleware, not the page.** Reading `cookies()` in the Server Component would opt `/` out of static generation — the last thing a marketing page wants — and Vercel runs middleware *before* the CDN cache, so the redirect still fires on a cached route. Crawlers carry no cookie, so **Googlebot always gets the landing page**; that is what makes the SEO work.
- **`wr_seen` is written CLIENT-SIDE by `<MarkVisited>` in the `(app)` layout, not by the middleware.** It used to be a `Set-Cookie` on any request to a product path, and that was wrong: **Next prefetches every `<Link>` that scrolls into view**, so merely *reading* the landing page fired requests to `/explore`, `/hub` and `/add` and marked the visitor as a product user — bouncing them to Explore next time they opened `/`, having never chosen to go there (fixed 2026-08-04). The header that identifies a prefetch (`next-router-prefetch`) is **not visible to the proxy** — Next strips it; the proxy sees only `accept`, `host`, `user-agent` and the forwarded set. `accept` does separate a document load from a prefetch, but a *client-side navigation* looks like a prefetch on that axis too, so keying on it would miss anyone clicking the hero CTA. An effect only runs when React actually renders, which is exactly the line wanted. Cost: the cookie can't be httpOnly. It holds no secret, and a crawler never gets it — which is what we want anyway.
- **Which screens count is decided by where `<MarkVisited>` is mounted** — the `(app)` layout: explore, hub, add, vendor, recon. `/terms` sits outside it deliberately (linked from the landing footer; reading the disclaimer shouldn't suppress the pitch), and so do the `(auth)` screens — visiting a login form isn't using the product, and anyone who completes it is caught by the signed-in check instead.
- **`/?ref=app` always renders the landing page.** Without an escape hatch the page is unreachable from inside the app — every link back would be bounced straight to Explore by the gate, because anyone clicking one has the cookie by definition. Both in-app links (`BrandFooter`'s lockup, `ProfileMenu`'s "About Wedding Recon") use `LANDING_HREF`, and so does the landing header's own wordmark. **Never link to a bare `/` from app code.**
- **A redirect response starts blank.** `NextResponse.redirect()` does not inherit the cookies `updateSession()` just wrote, so the gate copies them across; drop that loop and a session silently fails to refresh on any visit to `/`.
- Query strings survive the redirect on purpose (`/?types=venue` → `/explore?types=venue`), which is what lets a campaign link deep-link a filter.
- **Signed-in beats the cookie.** `updateSession()` now returns `{ response, claims }` instead of just the response, so the gate recognises an account holder on a new device or after a cookie clear at no extra cost — the `getClaims()` call was already being paid for on every request.

### Landing page content + SEO
- **All copy lives in `lib/landing/content.ts`**, not in JSX — every string, including section headings and the app-visual mock-ups. `FAQ_ITEMS` renders the accordion *and* the `FAQPage` JSON-LD, hence `answer` is a plain string: structured data cannot carry markup, and Google treats a visible/structured mismatch as a violation. The file opens with the editing rules; the two that bite are **no em dashes** (spaced hyphen instead, matching the enrich pipeline's own gate) and **US spelling**.
- **Page shape** (2026-08-04): hero → how-it-works stepper → four problem/solution rows → quick-facts deck → FAQ → CTA. The stepper owns `#how-it-works`, which the header nav anchors to; the hero's secondary CTA to it was removed, so that nav link is now the only thing holding the anchor alive.
- **The quotes in `PROBLEM_SOLUTIONS` are real people**, reproduced verbatim, consented to under first name + year + town (Kiara, 2026-08-04). Do not paraphrase, and do not let one name a vendor: no business is identified, which is what keeps an unflattering account a personal experience rather than a claim about a named business.
- **The FAQ is native `<details>`, not the Base UI `Accordion` used everywhere else.** The accordion unmounts a collapsed panel, so the answers would be absent from the HTML a crawler reads. `<details>` also needs no JS, which keeps the entire landing page a **zero-client-bundle Server Component**.
- **Nothing on the page is fabricated about a real business.** The hero's example recon card and the `AppVisual` mock-ups carry no vendor name — `place` is a county, never a business a reader could go and check. The "Example" badge was dropped as redundant (Kiara, 2026-08-04), so that anonymity is now the *only* thing marking those figures as illustrative. An invented quote attached to a named vendor would be a fake review of someone's livelihood — the same line the enrich pipeline draws with "negativity: sourced only, never synthesized."
- **App visuals are drawn in code** (`components/landing/app-visual.tsx`), not screenshotted: sharp at any size, no bytes, and they take their colors from `CATEGORIES` so they cannot drift from the real map. That file carries the swap point for real screenshots — capture those from a session with DB credentials, and look at what is on screen first, since a screenshot reads as authoritative in a way an illustration does not.
- **Stat figures are static constants measured 2026-08-01** (`DATA_SECTION`, `VENDOR_COUNTS`, `BEAUTY_SETUP`), sourced from `docs/vendor-filters-proposal.md` — deliberately not a live query, which would drop static generation on the one page that most needs it and render "0 vendors" whenever the free tier pauses. **Every derived percentage ships with its denominator.** Only quote a rate when BOTH answers get recorded: most booleans in that proposal ("shoots film", "BYO alcohol") are one-sided detections where silence means unknown, not no, and publishing one as a rate asserts something false about every undetected vendor. The hair-and-makeup split qualifies; that is why it is the one on the page.
- **Chart color was computed, not chosen.** The dataviz skill's palette validator rejected the ten category hues as bar fills — planner green vs food amber is ΔE 1.5 under deuteranopia, dj vs band 10 with normal vision (floor is 15). So magnitude rides bar length in a single hue and identity rides the icon swatch + label. The two-series split pair clears at ΔE 20.7 deutan. Re-run the validator before substituting any chart color.
- **Auto-advancing content needs three guards**, all in `how-it-works.tsx`: a pause control (WCAG 2.2.2, for anything moving unprompted past 5s), a permanent stop once the reader picks a step, and `prefers-reduced-motion` meaning it never starts. Every slide's text stays in the HTML regardless — inactive ones are `aria-hidden`, so crawlers read all three and a screen reader reads one.
- **Live vendor counts were deliberately left out** of the hero. "1,200+ Colorado vendors" is a strong trust signal but makes `/` dynamic and DB-dependent, and reads "0" whenever the free-tier project is paused. If it's ever wanted, add it behind ISR with a null fallback, not a bare query.
- **`app/sitemap.ts` includes public vendor pages** (capped at 20k, `revalidate = 86400`) — those are the long-tail search asset, thousands of URLs with unique recon on them. It uses a plain `@supabase/supabase-js` anon client rather than `lib/supabase/server`'s, because reading cookies would force the route dynamic and there is no session to honour. Everything is wrapped in try/catch returning the three static routes, so a paused project or missing env can't fail the build.
- **`title` on the landing page uses `{ absolute: … }`** — the root layout's `"%s · Wedding Recon"` template would otherwise append the brand to a title that already opens with it.
- **No city/category landing pages** (`/denver-wedding-venues` etc.) — considered and rejected for now (Kiara, 2026-08-04). Generating ~100 pages that are each just a filtered map is the doorway-page pattern Google penalizes. Revisit once a city+category has enough recon to support real aggregate content ("median venue quote in Boulder"), which is content those pages would then legitimately have.
- Brand green is now tokenized: `--brand` / `--brand-ink` / `--brand-soft` in `globals.css` (exposed as `bg-brand`, `text-brand-ink`, …). Same three values the logo and category `venue` already used. Existing hardcoded `#1D9E75` usages (bottom-nav, brand-mark) still resolve to the same color and were left alone.

### Sign-in: the code is the primary credential, the link is a convenience
- **An emailed link can never sign anyone in inside the installed PWA, and this is not fixable at the redirect layer.** `/auth/callback` verifies server-side and hands the session cookies back on its redirect, so they land in **whichever browser made the request** — and a mail client opens links in the default browser. On iOS a home-screen web app is a WKWebView with its **own website data store**, fully partitioned from Safari, so the browser completes the login perfectly and the app stays logged out. Reported 2026-08-06 as "the redirect opens in a browser so I can never get logged in on the PWA". Do not go looking for a redirect bug, a `scope` fix, or a deep link: there is no header, redirect, or manifest field that crosses an OS storage partition.
- **The fix is to remove the hop, not bridge it.** The email carries a numeric `{{ .Token }}` alongside the link; `components/auth/otp-code-form.tsx` calls `verifyOtp` **in the browser**, so the session is minted in the calling context's own cookie jar. `lib/supabase/client.ts` uses `createBrowserClient` (@supabase/ssr), which persists to **cookies**, not localStorage — that is what makes a client-side verify visible to the middleware and every RSC with no other plumbing. The link is kept for browser users; both credentials verify the **same OTP**, so whichever is used first wins.
- **This also fixes in-app browsers** (Instagram/Facebook link previews) and typed-on-phone/opened-on-laptop. Same root cause, same fix — which is why the code, not the link, is the one that leads.
- **Never assert the code's LENGTH in the client.** Supabase's OTP length is a project setting (Authentication → Providers → Email → Email OTP Length), settable 6–10; it defaults to 6 and **this project sends 8**. The form shipped with a hardcoded 6 and `maxLength` silently swallowed the last two digits as they were typed — correct code, correct email, an input that refused it, and no error anywhere (reported 2026-08-06). `otp-code-form.tsx` now bounds input at `MAX_CODE_LENGTH` 10 and enables submit at `MIN_CODE_LENGTH` 6, leaving Supabase the authority on whether a code is right. Same rule for copy: say "sign-in code", never a digit count, or the UI starts lying the moment someone changes that setting.
- **`postSignInPath()` (`lib/auth/post-signin.ts`) is shared by both completions** so they cannot disagree about where a login lands. The link path calls it inside `/auth/callback`; the code path navigates to `/auth/post-signin`, which exists only to run it. That navigation is `window.location.assign`, **never `router.push`** — the destination is decided from the cookies on that request, so they have to actually be sent.
- **Persisting the pending email is load-bearing, not polish** (`lib/auth/pending-otp.ts`). The code flow *requires* leaving the app to read the email, and iOS discards backgrounded PWAs aggressively, so "send code → switch to Mail → switch back" routinely returns to a **cold start**. Without the rehydrate, the couple lands on an empty login form holding a valid code with nowhere to type it — the exact failure the code was added to fix. It is **localStorage, not sessionStorage**: a relaunched PWA is a new session, so sessionStorage is already gone. TTL matches the OTP's own ~1 hour, and it stores an address, never a credential.
- **The guest Add-Recon flow is the strict case.** The draft (including photo `File`s) is in the PWA's **IndexedDB**, so finishing anywhere else loses it — the old "open it on this device" copy was true and still insufficient, because the app, not the device, was always the unit. On success it hands off to `/auth/post-signin` and lets `ResumePublishWatcher` pick the draft back up. **Do not shortcut straight to `/add?resume=1`**: that skips onboarding for a new account, publishing under a placeholder `user_` username with no TOS accepted.
- **`{{ .Token }}` must be pasted into BOTH Supabase templates** — "Magic Link" (existing user) and "Confirm signup" (brand-new address). Do one and new accounts silently get an email with no code in it. `useIsStandalone()` (`lib/use-standalone.ts`) only changes which instruction leads and what the warning says; both branches render the same controls, so there is no hydration mismatch and no control that appears or disappears.
- **`emailRedirectTo` at the two `signInWithOtp` call sites is currently inert.** The template renders `{{ .SiteURL }}/auth/callback` directly and never references `{{ .RedirectTo }}`/`{{ .ConfirmationURL }}`, so the option never reaches the email. Left in place because it is what a future template change would read, but do not try to thread a destination through it without changing the template too.

### Navigation with return context
- Use a `from` query param to track origin page (e.g., `?from=/explore` or `?from=/vendor/123`).
- Always validate: `from && from.startsWith("/") && !from.startsWith("//")` to prevent open redirects.
- Encode return paths: `encodeURIComponent(returnTo)` when serializing, `decodeURIComponent()` when reading (though next/navigation handles this).
- Example: guest clicks "Save" on vendor → redirects to `/login?from=/vendor/123` → after login, back button returns to that vendor (not Explore).

### React + SSR patterns
- **Portal rendering requires mounted state guard:** use `useEffect` with `setTimeout(..., 0)` to defer `setMounted(true)` (satisfies `react-hooks/set-state-in-effect` lint rule and ensures DOM exists).
  ```tsx
  const [mounted, setMounted] = useState(false);
  useEffect(() => {
    const t = setTimeout(() => setMounted(true), 0);
    return () => clearTimeout(t);
  }, []);
  ```
- **Portals escape containing block constraints:** `createPortal(el, document.body)` escapes `position: fixed` being relative to an ancestor with `backdrop-filter` or `transform`. Use for modals, drawers, popovers that need viewport-level positioning.
- **Server Actions + file uploads:** don't route image bytes through a Server Action — Next caps the action body at 1 MB, Vercel at ~4.5 MB. Compress + upload client-side directly to Supabase Storage and pass only the storage paths to the action (small structured data can ride along as a serialized arg). See **Recon photo uploads** below.

### UI layout & constraints
- Mobile frame: `max-w-[480px]` centered, tight padding, bottom nav always visible.
- Wider content (hub, vendor page): `max-w-[760px]` for better use of desktop space while staying readable.
- Bottom nav items: grid layout centered via `mx-auto` with the `max-w-[520px]` constraint (matches mobile frame + padding).
- Headers with profile menu: use `ProfileMenu className="ml-auto shrink-0"` to right-align; it auto-portals internally.
- **A `flex-1` item holding nowrap text needs `min-w-0`, and `truncate` is not a substitute.** A flex item's default `min-width: auto` floors it at its **min-content** width, so one `whitespace-nowrap` string inside (which is what `truncate` sets) becomes a width the item cannot shrink past — it overflows its row instead. The truncate classes only clip once the width is already definite; they cannot create the constraint. This is what pushed the Explore profile icon off-screen: the search box is `flex-1`, and its suggestion dropdown carries Nominatim area strings like "Denver, Denver County, Colorado, 80202, United States", so the box sat at 398px inside a 390px viewport (fixed 2026-08-06). **It only misbehaves when the long content is present** — the resting search bar looked perfect, so check the populated state, not the empty one.

### Supabase patterns
- **Idempotent upserts:** `upsert(..., { onConflict: "col1,col2" })` for operations that might repeat (e.g., save vendor to hub).
- **Case-insensitive uniqueness:** use a functional unique index `CREATE UNIQUE INDEX idx_name ON table (LOWER(col))` instead of relying on app-level normalization.
- **Vendor dedup:** 
  - Google Places path: upsert by `google_place_id` (guaranteed unique from Google).
  - Manual/user path: soft-dedup by `ilike("name", name)` + `ilike("city", city)` to catch duplicates, then insert if not found.
  - Pre-resolved vendor: lock the vendor type since it's canonical data; don't allow user to override.
- **RLS for public pages:** enable public read on `vendors`, `profiles.username`, `recon_entries` (filtered by status), `recon_media`; restrict write to authenticated users, update/delete to row owners.

### Form & field handling
- **Vendor type locking:** when adding recon for an existing vendor (via Hub "Add Recon" button), pass `vendorId` + `vendorType` as query params. Lock the type chip (read-only display) if both are present — the user cannot override.
- **Google Places integration:** server-side only; call `/api/places` route handler with an API key in `.env.local` (never exposed to client). Return place data (id, name, address, lat/lng) to client.
- **Image uploads:** compressed in the browser and uploaded **directly to Storage** (not through the action); the action only records `recon_media` paths. See **Recon photo uploads** below.

### Errors & gotchas
- **The whole app was silently rendering in Times New Roman** (found 2026-08-04). `globals.css` does `@import "shadcn/tailwind.css"`, which used to supply `--font-sans`; the `shadcn` package (a caret range, `^4.11.0`) **no longer ships that file** — it publishes only `dist/` — so the import resolves to nothing, `--font-sans` was empty, and Tailwind's `font-sans` utility emitted `font-family: var(--font-sans)` → browser default serif. Geist was being downloaded by `next/font` and assigned to `--font-geist-sans`, then never referenced. Fixed by defining `--font-sans: var(--font-geist-sans)` in `:root`. **Nothing fails loudly here** — the CSS import no-ops, the build passes, and a serif page just looks like a design choice. The check is one line in a browser: `getComputedStyle(document.body).fontFamily` should start with `Geist`.
- **Base UI + Radix confusion:** shadcn/ui wraps Base UI, not Radix — APIs differ. Check existing component files for patterns.
- **Console warning with render prop:** `<Button render={<Link>} />` triggers a warning; instead use `<Link className={buttonVariants()} />` directly.
- **Unique violation handling:** Google Places upsert can hit duplicate key; handle gracefully with `error?.code === "23505"` check.
- **Supabase free tier pausing:** after 7 days with zero requests, the project pauses (not deleted). Keep-alive is the daily `.github/workflows/keepalive.yml` ping of `/api/health` (repo variable `HEALTHCHECK_URL`). **A green run does not mean it worked** — it silently exits 0 when the variable is unset, and for weeks it was curling the apex domain, getting a **308** to the canonical host, and passing because the old test accepted any 2xx/3xx. `curl` does not follow redirects without `-L`, so Supabase was never touched. The step now uses `-L`, requires HTTP **200**, and greps the body for `"db":"ok"` — asserting on the payload, since the endpoint returns 200 even when its Supabase query fails. If you change the health check, keep it asserting on the body: status alone cannot tell you a query actually ran.
- **`getClaims()` over `getUser()` on read paths.** The project uses **asymmetric JWT signing keys**, so `getClaims()` verifies locally with no Auth-server round trip, while `getUser()` is always a network call. Used in `proxy.ts` (every request), the vendor page, the Hub, the recon-edit page, `ProfileMenu` (renders on nearly every page, and its `getUser()` sat serially in front of the profile query), and `useVendorPreviews`. **Writes keep `getUser()`** — `createRecon`, `updateRecon`, the auth callback, account actions — where the round trip is once-per-submit and catches a session revoked before its token expires. RLS re-validates the JWT at the database either way, so this is a latency choice, not the security boundary.
- **`generateMetadata` and the page share ONE vendor query, via React `cache()`.** They both need the row and each used to issue its own select, so every vendor page view paid two Supabase round trips for one row. `getVendor(id)` in `app/(app)/vendor/[id]/page.tsx` is wrapped in `cache()`, which dedupes within a single request render, so the second caller gets the first one's promise. It deliberately does the page's full `select("*")` even though metadata reads three columns: when the cost is a round trip rather than bytes, one wider query beats two narrow ones. Any new route that reads the same row in both places should do the same — the duplicate is easy to miss because both call sites look correct in isolation.
- **react-hook-form + React Compiler:** `watch("field")` triggers a benign "Compilation Skipped: incompatible library" lint warning (the compiler skips memoizing that component). Functionally fine; not worth chasing.

### Vendor search — one matcher, two bars (`lib/search/vendors.ts`)
- **Both search surfaces share one implementation.** The Explore bar (`/api/vendor-search`) and the Add Recon business box (`/api/places`) both call `searchVendors()` from `lib/search/vendors.ts`, which wraps the **`search_vendors` RPC**: token-AND over **name + `address_text` + `city`** (stop words dropped, every remaining token must appear — "the sanctuary" → "Sanctuary Golf Course"; stop-word list mirrored in `lib/search/tokens.ts`), then ranks by the **name-relevance scorer** that also lives there (`scoreVendorMatch`: exact > starts-with > word-boundary > contains > per-token, with a flat floor for rows that only matched address/city). **Change the matching or ranking rule in the RPC + that module and both bars move together** — don't reintroduce a per-route `ilike` chain or a second copy of the scorer.
- **Typo tolerance is a second tier, not a looser first one** (migrations `0026` + `0027`). Strict token-AND runs unchanged and, whenever it matches anything, is the whole answer — so no working query changes. Only when it finds **nothing** does a `pg_trgm` tier return up to 5 near-misses on **name** ("sanctaury" → "Sanctuary Golf Course"), every token needing to clear **`strict_word_similarity`** 0.35 (tokens under 4 chars must still match literally), ordered by the weakest token. **Use the `strict_` variant, not plain `word_similarity`** — the latter matches any trigram extent, including ones starting mid-word, which is how "sanctaury" pulled in "The Farmhouse Luxury Salon" at 0.400 ("…ury Sal…") next to real matches at 0.500. That junk isn't a weaker real match, so no threshold separates it; word-boundary extents drop it to 0.211 (`0027`). Those rows come back flagged `fuzzy` and scored **below every literal match** — a near-miss is a "did you mean", so it must never outrank what the user actually typed. Threshold and cap were tuned against real typo shapes vs. plausible-but-unknown business names; if you retune, keep the all-tokens-must-clear rule — it's what stops "mountain view lodge" matching "Spruce Mountain Ranch".
- What stays per-route is presentation only: row count, which fields render, `requireCoords` (Explore needs a pin to fly to, so coordinate-less vendors are dropped there and kept in Add Recon), and whether Google is blended in.
- `searchVendors` **never throws** — an unapplied migration or RPC error logs and yields no matches, so Explore still shows its Areas group and Add Recon still shows Google results.
- **Blended dedup (`/api/places`)**: searches Google Places autocomplete and our vendors **in parallel**, then merges. A Google prediction whose `place_id` matches an existing vendor is collapsed to the DB row (dedup — needs `google_place_id` from the RPC, added in `0024`). Existing rows are capped at 6 so a broad query can't crowd Google out of the 8 slots. Google predictions are scored with the same scorer (they carry no numeric score), which is what makes one ranked list possible.
- Returns a `SearchSuggestion` union: `{ kind: "existing", vendorId, vendorType, source, ... }` or `{ kind: "google", placeId, ... }`.
- Combobox (`components/add/places-combobox.tsx`) tags each row **"Google" / "User created" / "Featured"** (seed). Picking an existing vendor calls `onSelectExisting` → resolves straight to its `vendorId` (no new row, no Places details call) and **locks the type chip** (vendor type is canonical).

### Recon entry order within a vendor
- **One comparator, both surfaces** — `sortReconEntries()` in `lib/recon-sort.ts`, called by the vendor page's entry list and by `useVendorPreviews` for the preview card's text carousel, so the entry a card leads with is always the entry the vendor page leads with. It is a plain module with **no `"use client"`**, because the vendor page is a Server Component and the card is a Client one (the mistake `usesServiceRegion()` made). Three keys: **the viewer's own entry**, then **entries that state a price**, then **most recently collected**.
- **"Has a price" is a money-figure test, NOT "is `price_text` filled in".** `price_text` is **required on every bot-drafted entry** (`references/common/entry-rules-core.md`) and says so in words when a vendor publishes nothing, so a non-blank test sorts every entry into the priced tier — including the ones saying there is no price. `hasPriceQuote()` matches a currency symbol adjacent to a digit (or a digit next to `dollars`/`usd`). The no-price wording is deliberately **varied** rather than a fixed sentinel (see "Retiring the `Quote only` sentinel" below), which is a second reason the test reads the text for a figure instead of comparing against a known string.
- **A bare number is deliberately not a price.** Recon prose is full of digits that are guest counts, hours, party sizes and years ("Up to 150 attendees", "8-hr minimum", "2026 dates"), so keying off `\d` would put nearly everything in the priced tier. Validated against the 818 real quotes in `data/filter-extraction/vendor-filters.jsonl`: **97.2%** match, and every miss is a bare number lifted off a rate card ("Starting at 2200") — a shape recon text does not use, since the drafting contract writes `$` figures. The tier demotes rather than excludes, so a miss costs an entry a few rows, not visibility.
- **`price_details` counts, not just the headline.** The contract puts contract minimums and tier tables there, and a hedged-but-sourced range lands there under a no-price headline ("no formal quote, going off their published table, $4k-$6k"). Both fields render on the card, so a number in either is a number the couple gets.
- **Recency is the COLLECTED date, not `created_at`** (changed 2026-08-06; it was `created_at` before). The collected month/year is what the card displays, so ordering by anything else puts a card reading "Jan 2024" above one reading "Jun 2026" and just looks broken — and a quote's staleness is about when it was gathered, not when someone typed it in. `created_at` is the tiebreak (collected dates are month-granular, and bot entries are backdated to a random moment *inside* their collected month at upload, so it orders a month sensibly) and the fallback for pre-`0008` rows with no collected date. Both land on one millisecond axis, so the two kinds interleave correctly.
- **The comparator is total** — the result does not depend on the order rows arrived in, so neither surface relies on `sort()` stability or on the query's `order()` clause any more.
- **The preview card sorts the FLAT result once, before grouping by vendor.** Bucketing preserves relative order within each vendor's rows, and doing it there means the recon count, the fallback thumbnail and the slides all follow one order. Its query must **select `recon_collected_month`, `recon_collected_year` and `created_at`** — omit them and every row silently falls back, and the collected-date ordering quietly does nothing.

### Editing your own recon (`/recon/[id]/edit`)
- **The form fields are shared, the pages are not.** `components/recon/recon-form-fields.tsx` owns the zod schema (`reconFormSchema`) plus everything from the vendor-type chips down to the notes box; Add and Edit both render it. Deliberately **not** shared: the vendor picker and the photo uploader — Add resolves a vendor (search / Places / manual) while Edit locks it, and photos are add-only. Edit is its own route rather than an `?edit=` branch inside `/add` on purpose: a third of that page is guest magic-link + IndexedDB resume logic that is meaningless when editing (edit requires auth by definition).
- **Vendor and vendor type are never accepted from the client.** They are canonical *vendor* data that the form only displays, so `updateRecon` re-reads them from the row — the locked chip is enforced server-side, not just rendered. Moving a recon to a different vendor is not an edit; it would be a delete plus a new entry.
- **`usesServiceRegion()` lives in `lib/constants/categories.ts`, not the form module.** It gates the field in the form *and* nulls the column in the Server Action, and a `"use client"` module **cannot be called from the server** — putting it next to the form throws `Attempted to call usesServiceRegion() from the server` at save time. (Cost a debugging round on 2026-08-02.)
- **Editing is text-only for now.** `recon_media` has select + insert policies only (`0002_rls.sql`) — **no DELETE policy**, so removing a photo would silently no-op under RLS. Existing photos render read-only in the form with a note. Adding photo editing means a new migration for that policy *plus* teaching `ImageUpload` about already-uploaded paths (it is `File[]`-only today).
- **One entry per (vendor, author)** — enforced by the partial unique index in `0028` (excluding `removed`, so a takedown does not permanently block resubmission). The UI always assumed this; nothing enforced it. That is what lets the Hub map a vendor straight to one edit link.
- **Propagation is nearly free**, since both pages are dynamic (cookie-based client → no full-route cache). `updateRecon` calls `revalidatePath` on the vendor page + `/hub` purely to clear Next's **client-side Router Cache**, so a back-nav after saving does not show pre-edit copy. Map preview cards fetch per-mount and are already live.
- **Editing is reachable from the recon ENTRY only, never from a vendor card.** On the vendor page the entry's own badge is the control — `My recon | Edit ✎` — and it **replaces** the report button there (reporting yourself was never meaningful). Deliberately *not* on the Hub card (Kiara, 2026-08-03): a card is about the vendor, so an edit button on it is ambiguous about what it edits, and one entry point beats two. The Hub card's only action is **"Add"**, shown when you have no recon on that vendor yet — that one has no other one-tap home, since the vendor page's Add CTA is a navigation away. The big "Add recon" CTA on the vendor page stays hidden once you have an entry rather than flipping to "Edit".
- **A "back" that pushes instead of stepping back creates a bounce loop.** Explore → vendor → edit → back used to ping-pong between edit and vendor forever, never reaching Explore. Three compounding causes, all now fixed: the edit link dropped the vendor page's own `from` (it now threads the host page's **full URL including its query** via `ReconCard`'s `returnTo`); the edit page's back was a `<Link>`, which **pushes** a `from`-less `/vendor/X` whose own BackButton then `router.back()`s into the edit page; and the post-save redirect dropped `from` too. Rules that fall out of it: when a page can be returned to, pass its **whole** URL as the return target, not just its pathname; a back control must step through history (`router.back()`) rather than push, since only a real back step lands on the entry that carries the return context; and gate that on a **deterministic** signal — the presence of `from`, meaning we were linked in-app — not on `window.history.length`, which counts a fresh tab's blank entry. A cold arrival `replace`s rather than pushes. The save redirect uses `RedirectType.replace` so a submitted form is not reachable by pressing back.
- **Google photos are sized per surface via `?w=`.** `/api/vendor-photo` takes an **allowlisted** width — `300` (card thumbnails: hub + map preview cards, 96 CSS px at 3x), `600` (vendor-page strip, 200x150 at 3x), `1200` (lightbox, and the default when `w` is omitted). It used to serve 1200px to everything, so a 96px card shipped ~17x the pixels it drew and a Hub of 20 vendors pulled megabytes of JPEG for thumbnails. Keep the allowlist small: each width is a separate CDN cache key **and** a separate billed Google fetch (~2x per photo per month with the 30-day TTL absorbing the rest). Off-allowlist widths 404 rather than clamp, so junk cannot alias onto a valid entry. Note there is **no `next/image` anywhere** — deliberate, since Vercel Image Optimization is billed and explicit `?w=` on a plain `<img>` is free.
- **A dynamic route needs a `loading.tsx` or its link feels broken.** `/recon/[id]/edit` shipped without one and users reported tapping Edit several times with nothing happening. Measured on a throttled phone profile: **2052ms with the *previous* page still on screen** and zero indication the tap registered — Next has no loading boundary to swap in, so it just waits out the server round trip (auth check + entry fetch). Adding `loading.tsx` cut first feedback to **379ms**, and it doubles as the prefetch target for `<Link>`. Any new dynamic route under `(app)` should get one; `/vendor/[id]` already had one, which is why it never felt this way.
- **Small badges need a grown touch area, not a bigger badge.** The `My recon | Edit` pill is ~20px tall — under the 24px WCAG floor and well under the 44px iOS guidance — and was routinely missed on a real phone. Fixed with a transparent `after:absolute after:inset-x-0 after:-inset-y-3.5`, which takes the effective touch height to ~47px while the pill stays visually 20px. Vertical-only on purpose: the pill is already ~110px wide, and expanding horizontally would reach neighbouring controls.
- **Recon card headers wrap, they do not truncate.** The username is the person's identity, so `CardHeader`'s meta row is `flex-wrap` and the tags (My recon/Edit, recon type, collected date) move to a second line before the name is ever clipped. `CardAction` is omitted entirely — not rendered empty — on your own entry, since `has-data-[slot=card-action]:grid-cols-[1fr_auto]` would otherwise reserve a dead column and squeeze the name.
- **Gotcha — `buttonVariants()` needs `cn()`.** Calling it raw emits both the base `border-transparent` and the outline variant's `border-border`; equal specificity means stylesheet order decides and the border comes out invisible. `cn()`'s tailwind-merge drops the loser — that is why `Button` itself does `cn(buttonVariants({...}))`. Separately, `AccordionContent` styles every descendant anchor with `[&_a]:underline`, which out-specifies a plain utility, so a Link-as-button inside it needs `no-underline!`.

### Recon photo uploads (client-side compress + direct-to-Storage)
- Photos are **compressed in the browser** (`lib/image-compress.ts` — ~1600px full + ~400px thumbnail, JPEG) and **uploaded straight to Supabase Storage** (`lib/recon-upload.ts`); they never pass through the `createRecon` Server Action body. This sidesteps Next's 1 MB action-body cap **and** Vercel's ~4.5 MB serverless limit, and is the main lever on Storage/egress cost (~10× smaller files).
- `createRecon` (`app/(app)/add/actions.ts`) takes the typed input **directly** (no FormData) and only **records media paths** on `recon_media` (`storage_path` + `thumb_path`). Uploads land under `${userId}/<submissionUuid>/…`.
- Picker (`components/add/image-upload.tsx`): **max 4 photos, 50 MB each** (per-file, client-side); the bucket also enforces a 50 MB `file_size_limit` (migration `0010`) as a server-side backstop.
- Display: `recon-card.tsx` previews use `thumb_path ?? storage_path` (egress saver); the vendor-page carousel uses the full image. Reads select `recon_media(*)`, so a missing `thumb_path` is null-safe on pre-migration rows.
- **Guest flow:** raw photos are stashed in IndexedDB and compressed + uploaded on **resume** (post-auth), since Storage RLS requires an authenticated uploader.
- Storage RLS (`0005_storage.sql`) already lets any authenticated user upload to `recon-media`; Supabase stamps `owner = auth.uid()` so the owner-only update/delete policies still apply — **no new policy needed** for client uploads.

### Literal `\n` in recon text (escape sequences, not newlines)
- **Symptom:** a bot recon renders `…as a team on shoots\n-she's described as…` mid-sentence on the vendor card (reported 2026-08-04). The stored text holds the two-character **escape**, not a newline; `recon-card.tsx` renders `notes`/`price_details` with `whitespace-pre-line`, which honors real newlines and prints an escape as what it is — text.
- **Why it got all the way through.** Every stage had a reason not to catch it: draft workers emit one JSON object per row and the contract asks for `notes` on **one logical line**, so a worker wanting a bullet break writes `\n` (`JSON.parse` of `"\\n"` yields backslash + n, never a break); `readWorkerRows` in `pipeline.mjs` normalizes only **real** newlines (`/\r?\n/g`); `csvEsc` sees no newline so it does not even quote the cell; and `debullet()` in `upload.mjs` keys off **whitespace** before a `-bullet` — the preceding char here is the `n` of the escape, so it never fired and the bullets never became lines either.
- **Fix, at the layer that owns each part.** `upload.mjs` `unescapeBreaks()` converts the escapes at insert (all three prose columns, run **before** `debullet` so the char in front of a bullet is real whitespace); `pipeline.mjs status` **counts** them at the cheap pre-check; the draft contract now says the escape does not produce a line break and to separate bullets with a space; migration `0031` repairs the rows already written.
- **This one is repaired, not rejected** — unlike the BANNED/PROCESS/RESEARCH/EMDASH gates, which hard-fail. The row is otherwise fine and the correction is unambiguous, so failing an upload over it would be pure friction. That is why `status` reports a count rather than an error, and why the "keep these in lockstep with `upload.mjs`" rule above covers the three **gates**, not this.
- **Watch the `{1,2}`:** the doubly-escaped form (`\\n`) shows up too, and the CR+LF pair must be collapsed **first** or it yields two blank-looking breaks instead of one. In the SQL, patterns are composed from `chr(92)` rather than backslash literals so the migration does not depend on `standard_conforming_strings`, and the match uses the regex operator `~` — **never `LIKE`**, whose default ESCAPE character is a backslash, so `like '%\n%'` quietly tests for a bare letter `n`.

### Retiring the `Quote only` sentinel
- **Two defects in one string** (Kiara, 2026-08-07). The drafting contract made the literal `Quote only` the `price_text` value for a vendor that publishes nothing. It was (1) written even on entries that stated a figure — "Quote only but the knot says $8k" contradicts itself, and **if we have a number we have a price data point** — and (2) jargon: a couple reads it as a category label, not as "nobody would tell us a price".
- **The replacement is plural on purpose.** `No quote provided` / `No quote found` / `Didn't get a quote`, varied across entries. A fixed sentinel is what made a page of recon read as one template, so **do not reintroduce a canonical string** — and note that nothing may key off one, which is why `hasPriceQuote()` reads the text for a money figure instead (see "Recon entry order within a vendor").
- **The wording is a claim about US, not about the vendor**, and that is load-bearing. "We did not get a quote" stays true when `price_details` cites a third-party figure below it; "quote only" does not, because it asserts a quote is the only route to any number. That distinction is what lets the headline and the details disagree in tone without lying, and it is why the checks below are **per field** rather than per entry.
- **Scope is the quote-only family and nothing wider.** "No published pricing", "Contact for pricing" and friends are left alone: already plain English, still true next to a third-party number, and they add real variety. Widening the regex to them would churn text that was never the problem.
- **Split by whether the fix is mechanical.** The wording alone is **repaired** at insert (`plainQuoteOnly()` in `upload.mjs`), same call as the `\n` escapes. The phrase sitting next to a money figure in the same field is a **hard gate**, because what that headline should say instead is editorial — a script cutting the clause would hide a drafting error rather than fix it. `pipeline.mjs status` counts both at the cheap pre-check so neither first surfaces at upload.
- **Migration `0036` rewrote the rows already written**, on the same split: Rule A cuts the quote-only clause and lets the number lead ("Quote only but The Knot says $8k" -> "The Knot says $8k"); Rule B swaps the wording, picked from the entry id so a re-run cannot re-randomize. Gated on `profiles.is_bot` — **a real person who typed "quote only" wrote their own words** and must never be edited.
- **Mid-sentence occurrences are left verbatim, everywhere.** A blind swap produces "they are no quote found so you email them", and the qualifier prefix genuinely occurs in prose ("we asked for a price quote only after the tour"). Only a phrase that OPENS the field or closes it as its own fenced clause is touched; the migration ends with a REVIEW query listing the residue (including `notes`, which it never rewrites) as a hand-fix worklist. **That query is a worklist, not an assertion of zero** — unlike `0031`.
- **The money test is one predicate in three languages** — `MONEY` in `lib/recon-sort.ts`, the same regex in `pipeline.mjs`/`upload.mjs`, and a backslash-free twin in `0036`. Verified identical against all 818 real price quotes in `data/filter-extraction` (zero disagreements), which is also what says the SQL twin is faithful. Keep them in lockstep; a bare number is deliberately **not** a price.
- **`pipeline.mjs merge` used to count "real pricing" as "price_text does not start with `quote only`"** — wrong in both directions, since an entry citing a figure under a quote-only headline counted as unpriced and any other empty wording counted as priced. It is the `MONEY` test over both columns now, so the number predicts where the batch lands in the Explore list.

### External-link overlay (`<ExternalLink>`)
- All external links go through `components/external-link.tsx` — a real anchor (cmd/ctrl/middle-click keep native behavior) that intercepts a plain left-click to show the destination in a full-height overlay sheet (`components/external-overlay.tsx`, photo-lightbox portal pattern) with domain + open-in-new-tab + ✕ header and a sandboxed iframe (**no** `allow-top-navigation`, so framebusting scripts can't hijack the app tab).
- **Framing is the target site's choice** (X-Frame-Options / CSP `frame-ancestors`) and invisible to cross-origin JS, so embeddability is checked server-side: `embed={{ vendorId, kind }}` hits `/api/embed-check` in the background on mount (URL resolved from the vendors row — no raw-URL param, so no SSRF; failures → `false`; cached 1h browser / 24h CDN). Blocked or unchecked links behave exactly like `<a target="_blank">` — no dead-end taps.
- Static cases skip the check: **Instagram** profiles always block framing (`embed` omitted → plain new-tab link); **Google Maps** overlays the keyless iframe-embeddable view (`maps.google.com/maps?q=<name+address>&output=embed`) via `embedSrc` + `embed`. That endpoint is undocumented-but-ancient Google; if it ever dies, swap to the official (also free) Maps Embed API with a referrer-restricted key.

### Vendor page media block — one photo strip, short map

It was two stacked strips — `GooglePhotoStrip` + `PhotoCarousel`, both now deleted — kept apart so community snaps never read as official marketing. ### Service region drives two location signals
- **`usesServiceRegion(vendorType)` is the one switch** (`lib/constants/categories.ts`), backed by the `FIXED_LOCATION_TYPES` list: `venue`, `hotel`, `dress`. It already gated the recon form field and the `service_region` column; it now also drives the **map pin halo** and the **vendor-page map preview**. Add a type to that list and all four move together — never re-derive the test anywhere else. The rule is *does the couple go to them, or do they travel to the couple*: a bridal shop is a storefront you book an appointment at (`dress` moved here 2026-08-04, migration `0030`), while a florist has a shop but delivers and installs at the venue, so its travel radius is a real cost and it stays service-area. The enrich pipeline mirrors the same list as `serviceRegionRequired` in `etype.mjs` — keep the two in sync.
- **The halo is baked into the existing image ids, not a new variant axis.** Because it is a pure function of `vendor_type`, `lib/map/pin-images.ts` just draws `pin-flowers-solid` with a glow; `vendor-map.tsx` is untouched — no new layer, filter, source, or feature property. Service-area categories get bigger boxes (48/64/60 vs 36/52/48) to hold the glow; the disc radius is unchanged, and box size does not affect placement (`icon-allow-overlap` + `icon-ignore-placement`) or label offsets (ems of text-size), so nothing else moves.
- **The glow is deliberately edgeless**, a radial gradient that never resolves into a border. The other two pin signals are hard-edged and must stay separable at a glance: a **dashed** outline means "approximate address", a **crisp ring** means "this pin's card is open". Note ~10 of 12 categories are service-region, so on an unfiltered map the halo is closer to texture than to a badge — that is why peak alpha is low (`HALO_ALPHA`, the tuning knob). Inverting it (marking the two fixed-location types instead) is the obvious alternative if it ever reads as noise.
- **Gotcha — SVG gradient ids resolve per DOCUMENT.** Each rasterized pin is its own data-URI document, so a fixed `id="halo"` is safe there; but `vendorPinMarkup()` injects the same markup **inline** into the page, where a second pin sharing the id silently paints itself in the first one's color. Caught in review: a contact sheet of all categories rendered the blue Photos pin with the pink Flowers glow. Ids are namespaced `wr-halo-<type>-<box>`.
- **The glow is a separate unshadowed canvas layer.** `rasterize()` takes layers and applies the drop shadow per layer, because a blurred dark copy of a soft glow reads as grime. The disc keeps the exact shadow it always had, so haloed and un-haloed pins stay identical where they overlap.
- **The vendor page mirrors the split in one slot** (below the photos, above the recon): a fixed-location vendor gets `VendorMapPreview`, a service-region vendor gets its **service areas in words**, deduped from its recon entries' `service_region` (rendered only when that data exists — it explains the missing map rather than decorating the gap).
- **The mini-map is free.** MapLibre + the same OpenFreeMap tiles Explore uses — deliberately **not** Google Static Maps, which bills per image. It is `interactive: false` (a drag-to-pan map inside a scrolling column traps the touch gesture), and it initializes **on mount**, like `vendor-map.tsx`. The pin comes from the shared `vendorPinMarkup()` so it is pixel-identical to the one just tapped on Explore, dashed outline included.
- **Gotcha — never size a MapLibre container with `absolute inset-0`.** MapLibre stamps `.maplibregl-map` onto whatever element you hand it, and maplibre-gl.css declares that class `position: relative`. That is the SAME specificity as Tailwind's `absolute`, and the library stylesheet loads after Tailwind's utilities, so it wins: the container stops being positioned, `inset-0` no longer sizes it, and because every child MapLibre adds is itself absolute it collapses to **zero height**. Canvas, marker and attribution are all in the DOM and all invisible. Give the container an explicit `h-full w-full` inside a sized wrapper — which is why `vendor-map.tsx` never hit this.
  - This was the blank vendor-page preview reported 2026-08-04, and it cost two wrong fixes first. The diagnosis that worked was the **`verify` skill** (fake PostgREST + Playwright) probing the live DOM: `wrapSize 356x174` next to `innerSize 356x0` named the bug in one shot, after reasoning from screenshots had twice pointed at the wrong thing. Reach for it early on "renders but looks wrong" — a DOM probe beats inference. The symptom to recognise: **no attribution visible either**, since an AttributionControl inside a collapsed (or style-less) map renders empty, so missing credit means the map is broken rather than the tiles.
  - Init is gated on **`requestIdleCallback`, not on visibility** (2026-08-06). An IntersectionObserver gate was tried and removed while chasing the blank-preview bug above; it was not the cause, and it is still the wrong tool — on a 390x844 phone this map sits *inside* the first viewport, so a visibility gate fires immediately and saves nothing. But the note that replaced it ("the dynamic `import()` already keeps MapLibre in its own chunk, nearly all of the saving") was wrong on the part that matters: a separate chunk keeps MapLibre out of the *initial bundle*, yet a mount-time effect downloads and executes it immediately anyway, so it lands in the initial load regardless. **Measured** on the built app: a venue page went 529 KB / 40 requests before this preview existed to 850 KB / 45 after — +1.2 MB decoded JS, a ~466 KB MapLibre worker blob, and a basemap fetch to `tiles.openfreemap.org` (a third-party origin, so a fresh DNS + TLS handshake before the style/sprite/glyph/tile fan-out even begins), all racing hydration and the photo strip. Scheduling is the right axis: the map is an orienting glance, not the content. `requestIdleCallback`'s **`timeout` is load-bearing** — it guarantees the callback runs, which is precisely what the observer could not promise, so the permanently-grey-box failure cannot recur; browsers without it (Safari < 16.4) fall back to a short `setTimeout`. Measured after: page chunks finish at +358 ms, the map starts at +568 ms. Note this **reorders** work, it does not remove bytes — the payload is inherent to putting a WebGL map on the page, so if vendor-page weight is the problem, the lever is gating the map behind a tap, not tuning the delay.
  - Two guards came out of it: `map.resize()` on load (MapLibre measures its container once at construction and never watches it), and an `error` handler that logs, since a failed style is otherwise completely silent.
  - The compact AttributionControl starts **expanded** (`maplibregl-compact-show`), which costs 44px of a 174px preview; the `load` handler removes that class so it collapses to the "i". Credit stays one tap away, which is what the compact affordance is for — remove the class rather than overriding the CSS, or the toggle stops working.
- **The "View larger map" chip is TOP-right on purpose.** MapLibre's compact attribution collapses to an "i" only on a narrow map and expands to a full-width credit bar on a wide one, which landed straight on top of a bottom-right chip on desktop. Basemap attribution is required by OpenFreeMap/OSM, so it also has to stay clickable: the tap overlay is `z-[1]` and the control corner is lifted with `[&_.maplibregl-ctrl-bottom-right]:z-[2]`.

### Approximate-location map pins
- `isApproximateLocation(vendor)` heuristic: **non-Google source + no digit in the address** ⇒ approximate (geocoded to a city/region centroid, not a street address). Known blind spot: numbered street names ("E 17th Ave") read as precise. The robust replacement is to **store geocode precision at save time** (Nominatim returns `addresstype` + a `boundingbox`) and key off that field instead.
- Approximate pins get a **dashed** white outline (vs solid); pins sharing a rounded coordinate are **fanned out** across a compact phyllotaxis disc (`~110m·√n`, deterministic by vendor id so they don't jump on pan). Both live entirely in `vendor-map.tsx` — no migration, since the RPC already returns `source`/`google_place_id`/`address_text`.
- For very large piles (~50) the fan-out only fully separates at city zoom; if that becomes common, add a click-to-list drawer (discussed, not built).

### Pin labels + the single-pin peek card (Zillow pattern)
- **One preview card, FOUR surfaces.** `components/map/vendor-preview-card.tsx` owns both the card (photo → category pill → name → **"City, ST" locality** → recon count, plus the swipeable recon-text carousel) **and** its data fetch (`useVendorPreviews(ids)`). The cluster feed, the on-screen results feed, the single-pin peek (`vendor-pin-preview.tsx`), **and the Planning Hub** (`hub-accordion.tsx`) all render it — change the card there and every surface moves together. Don't re-inline a second copy. The card's main control is a **`<Link href>`, not a button calling `router.push`** — that is what gets `/vendor/[id]`'s `loading.tsx` prefetched, and without it Next does not know the route has a loading boundary until the whole RSC response lands, so a tap sits there doing visibly nothing. Measured in the results feed with card photos still in flight: **821ms tap-to-navigation as a button, 241ms as a Link**. It reported as "I cannot click the card until its photo loads" (Kiara, 2026-08-04) — the click was in fact registering within ~45ms; the photos were simply competing for bandwidth with the un-prefetched navigation, so the two finished together. Same lesson as `/recon/[id]/edit`. Surfaces pass `href` plus an optional `onNavigate` for side effects (the feed saves its scroll position there); the recon carousel below the link still navigates via `router.push`, since a horizontally scrollable strip cannot live inside an anchor. **The link needs `no-underline!`** — in the Hub it sits inside `AccordionContent`, whose `[&_a]:underline` out-specifies a plain utility. Two props flex it per surface instead of forking it: **`showCategoryPill`** (off in the Hub, where cards already sit inside a category accordion) and **`action`** (a trailing control — the Hub's "Add" button — rendered as a **sibling** of the main button, never nested inside it). `useVendorPreviews` also resolves the viewer via `getClaims()` so **their own recon sorts first in the carousel and is tagged "My recon"**, matching how the vendor page orders its entry list (the shared comparator — see "Recon entry order within a vendor" below); Explore is public, so a null viewer is normal and the "mine first" key and the tag are simply no-ops.
- **The feed pages 20 at a time, and `useVendorPreviews` caches by id.** Reported as "list view takes 5-10 seconds, especially past 20 vendors, but only sometimes" (Kiara, 2026-08-06). The feed was handed up to `MAX_VISIBLE_ENTRIES` (200) rows and asked for previews of all of them at once — and the preview fetch pulls **every active recon entry for every id**, full `notes`/`price_details`/`price_text` prose plus a `recon_media` join, to render a two-line truncated carousel. Measured against a realistic corpus at 119 vendors: **237 recon rows, 171 KB, on a request URL of 4,770 characters** (200 ids is ~8 KB, at or past what gateways will carry — which is the likeliest source of the intermittency, since the URL grows with how many pins are in view). `VendorFeed` now renders `entries.slice(0, shownCount)` and grows by `FEED_PAGE_SIZE` from an IntersectionObserver sentinel with 600px of runway. Throttled 4x-CPU/1.6 Mbps: **1352ms -> 423ms to first cards**, with the page query at 40 rows / 29 KB on a 998-char URL.
- **Note what was NOT the problem: rendering.** The feed already had `content-visibility:auto` + `contain-intrinsic-size` per row and `loading="lazy"` on card images, so off-screen cards cost nothing to paint. Paginating the DOM would have bought nothing; the fix is windowing the **query**. Check which one you are actually paying for before adding virtualization.
- **`useVendorPreviews` must never blank on a growing list.** It used to `setItems(null)` at the top of its effect, so any id-set change dropped the whole feed to a spinner — including paging in more rows, which would have made windowing worse than the disease. It now keeps a `Map<id, VendorPreview>` and fetches **only ids it has never seen**, returning null solely when it has nothing at all. The split matters: the cache is **state** (the render reads it, and a ref cannot be read during render) while the seen-set is a **ref** (the effect reads it, and depending on the cache it just wrote would loop). Ids are marked seen when *requested*, not when returned, so a deleted vendor is not re-requested forever. Cache is dropped wholesale past `PREVIEW_CACHE_MAX`.
- **Two React rules bite here and both have a right answer that is not a suppression.** Resetting the window when the entry list changes is done by **setting state during render** (React's documented "adjust state when a prop changes"), not in an effect — an effect sets it after paint, so the couple sees a frame of the previous list, and it trips `react-hooks/set-state-in-effect`. And the derived list is a `useMemo` over **state**, because `react-hooks/refs` correctly rejects reading `ref.current` during render.
- **The card's locality subtitle comes from `formatVendorLocality()`** (`lib/vendor-locality.ts`), shown for **every** vendor type. `city` + `region` are the source of truth; `address_text` is parsed only to fill a gap, scanning from the END and accepting a state **only in the last two comma segments** — without that guard a street name carrying a state abbreviation ("Mt Vernon Rd" → MT) hijacks the parse and drags a junk city along. A bare state with no city renders as nothing, since "CO" alone reads as a data glitch. `normalizeRegion()` doubles as the is-this-a-state test: it returns unmapped input unchanged, so *requiring a clean 2-letter result* is what makes it reliable. The Hub's loading skeleton renders the locality too (it has the vendor row server-side already), so cards don't gain a line when previews land.
- **One list sheet, two feeds.** `components/map/vendor-list-sheet.tsx` is the bottom-sheet feed itself (portal, backdrop, scroll lock, swipe-down, scroll restore). It takes `entries: {id, vendorType, rank?}[]` — **a type per row**, so a feed can mix categories — plus a `heading` and the `scrollKey` its scroll position parks under. `cluster-list-sheet.tsx` is a thin wrapper over it; the results feed passes mixed rows straight through. **Both feeds arrive pre-sorted by the map**, via the shared `compareRanked` — see "List view order".
- **A pin tap peeks, it doesn't navigate.** `VendorMap` calls `onVendorOpen` and Explore floats the card over the bottom of the map; tapping the *card* is what opens `/vendor/[id]`. The peek is deliberately **not** a modal — no portal, no backdrop, no scroll lock — so the map stays pannable and the next pin tap just swaps the card. Dismissed by the ✕, Escape, a swipe down, or a tap on empty map (`onBackgroundTap`, which fires when `queryRenderedFeatures` hits no pin/cluster layer). With no `onVendorOpen` wired up, a pin tap falls back to navigating straight to the vendor page.
- **Names on pins from zoom `LABEL_MIN_ZOOM` (= 12).** It's a standalone constant, deliberately *below* `CLUSTER_MAX_ZOOM` (14) so names appear earlier on the way in — it used to be `CLUSTER_MAX_ZOOM + 1` on the reasoning that cluster bubbles must be gone first, but that was never the thing making a label unambiguous: the pin layer is filtered to unclustered points, so a labelled feature is a single vendor at any zoom. Labelling below the cluster ceiling just means the names you get are the isolated pins between bubbles, with the crowded ones collide-dropping. Still at/below the zoom a vendor search flies to, so a searched pin arrives named. Labels are `text-field` on the existing pin layers (no new layer): `["step", ["zoom"], …]` with the zoom test at the **outermost** level, which is what lets a layout property mix zoom with a per-feature `["get","name"]`. `text-optional` + no-overlap means crowded labels **collide-drop** while the pin always renders (the icon ignores placement entirely).
- **The selected pin** (the one whose card is open) swaps to an **emphasized pin image** — a bigger disc inside a category-colored ring, `pinImageId(type, approximate, true)` in `pin-images.ts`, rasterized alongside the plain ones at load — and gets a larger name label at *any* zoom. All of it is layout expressions on the existing pin layers (`selectionLayout()` + `applySelection()`, same shape as `applyTypeFilter()`), keyed off an `iconSelected` feature property, so a selection change is four `setLayoutProperty` calls per type with no new layers or sources. A plain scale-up was tried first and wasn't readable enough next to its neighbours.
- The peek card renders **above** the brand-mark/locate control row (both inside one `mt-auto` bottom stack), so opening it doesn't push those controls up and out of reach. A pin tapped inside the bottom `PREVIEW_SAFE_PX` (300px — card + that row + the attribution gap) is **panned up** so the card never covers the pin it describes.
- **Restore-on-return** mirrors the cluster sheet: `wr:pin` in sessionStorage + `?from=/explore?restore=1`. The two are mutually exclusive (opening one clears the other's key). The URL marker is consumed **inside** the deferred `setState`, not before it — in dev React mounts twice and the first pass's cleanup cancels that timeout, so dropping the marker up front left the second pass with nothing to restore.
- **Every overlay over the map opts IN to pointer events; nothing inherits them.** The whole over-the-map stack sits in one `pointer-events-none absolute inset-0` box (added when the list view needed a bounded height), so a control that does not carry `pointer-events-auto` is inert — the tap goes straight through to the MapLibre canvas. That silently broke the entire top bar (brand mark, search bar, profile menu) and the bottom stack (pin peek card, locate button); the two rows that were written after the wrapper had it, the two that predated it did not (fixed 2026-08-06). Put `pointer-events-auto` on the **individual controls**, never on the row: each row is a full-width band, and the gaps between controls have to stay pannable map. That is also what retired the old "the bottom row eats every map tap in its ~90px band" note — the row is click-through now and only the button itself takes taps.
  - **Nothing fails loudly**: the control renders, hovers, and looks correct; it just does not respond. The one-line check is `document.elementFromPoint(x, y)` at a control's centre — if it returns `canvas.maplibregl-canvas`, that control is dead. Playwright's own hit-target check catches it too (`page.click` times out rather than clicking through).

### Explore's fetch does not wait for the map
- **The vendor query starts at MOUNT, before MapLibre is even downloaded.** It used to live inside `map.on("load")`, which put it at the end of a chain it had no real dependency on: download the ~1 MB MapLibre chunk, construct the map, fetch the basemap style from `tiles.openfreemap.org`, parse it, fire `load`, *then* ask Supabase for pins. Measured on a 4x-CPU / 1.6 Mbps / 150 ms profile, the style request had not even **started** until +5.9 s — the pins were queued behind a third-party CDN for nothing. After the change the query fires at **+2.9 s**, about 4.3 s before the style request, and the map still only issues **one** `vendors_in_bbox` on load.
- **What made it possible is that a bbox is a pure function of center, zoom and container size**, all known at mount — so `lib/map/viewport.ts` computes it (Web Mercator, 512 px tiles, matching MapLibre's transform) instead of asking `map.getBounds()`. `fetchVendors()` was split into `fetchBbox(box)` (explicit box, no map needed) and the map-reading wrapper.
- **The prefetch result is not plumbed into the load handler — it is handed over through `coverageRef`.** `fetchBbox` records the box it fetched as covered, so the `fetchVendors()` call inside `load` sees an ordinary cache hit, returns null, and the handler applies the prefetched rows. That is why there is no second query and no new synchronisation to reason about: it reuses the pan cache that already existed. If the container has not been laid out, `bboxForView` returns null and it falls back to the old fetch-after-load path.
- **The remaining floor is hydration, not the map.** +2.9 s is when React can first run an effect on a throttled phone. Going below that means server-rendering the initial rows into the page, which is a different (bigger) change.
- **`filters` is fetched lazily and merged in** (migration `0034`). `withFilters` latches true when the filter sheet is first opened — not on the first chip tap, so the fetch overlaps the couple reading the sheet — and from then on later pans fetch pins and attributes together. Before they land every vendor ranks 1 (unfiltered), so the transient is "nothing has dimmed yet", never a wrong answer. Verified end to end: initial load 1 vendors / 0 filters, sheet open 0 / 1, pan off coverage 1 / 1.

### "See all N results on screen" (the results pill)
- **The count is computed in the map, not the page.** `vendor-map.tsx` keeps the last applied rows + their resolved display positions in refs and answers "what's on screen" against `map.getBounds()` on every settled move, after new rows land, and on a type-filter change — emitting `{ total, entries }` via `onVisibleVendorsChange`. It's deliberately **not** `queryRenderedFeatures`, which answers "what's rasterized": that collapses clusters into one feature and misses pins outside the painted tiles. Positions come from the same fan-out resolver the pins use, so the count matches what's drawn.
- **Recount on `moveend` is immediate**, not on the debounced refetch — the pill has to track the viewport. It's pure in-memory work over rows already held, and a pan that changes nothing emits nothing (the payload is diffed by an id key), so no re-render churn.
- **The filter is respected for free** — the same `selectedTypes` that toggles layer visibility gates the count, so multi-type selections just sum. The feed mixes those types in one list; `screenListHeading` only names a category when the list is unambiguously one type (user filtered to exactly one, or a complete list happens to be homogeneous).
- **Capped at `MAX_VISIBLE_ENTRIES` (200) rows, nearest the map center first** — `useVendorPreviews` puts every id in one PostgREST `in.()` filter, and a few thousand uuids would blow the URL limit. `total` is always the true count (the pill must not lie); when the list is capped the sheet says so in a footnote. If a deeper list is ever wanted, paginate the feed rather than raising the cap.
- **The open list is a frozen snapshot** (`wr:screen` in sessionStorage, scroll under `wr:screenScroll`), for the same reason the cluster feed is: the sheet is modal, and a list reshuffling under a scroll would be unusable. It's mutually exclusive with the cluster sheet and the pin peek — opening any one clears the other two keys.

### List view order
- **Five keys, in `compareRanked()` in `vendor-map.tsx`** — `rank`, then `matched`, then `priced`, then `photo`, then distance from the map center. **BOTH feeds use it**: the on-screen results list (`reportVisibleVendors`) and the tapped-cluster sheet. The cluster sheet used to render `getClusterLeaves()` order, which is supercluster **tree** order — spatial-index insertion order, arbitrary to a reader — so the same two vendors came out differently depending on which way the list was opened (reported 2026-08-07: a "No quote found" photographer above one quoting $2.5k). The scoring is `rankVendor()`; a sixth key goes in those two functions and both feeds move together. Each only reorders within the tier above it, so distance still decides at the bottom. The same comparator serves the unfiltered list and the filtered one; with no filter active every row is rank 1 with `matched` 1 and both keys simply drop out.
- **The partial tier is itself graded, by `matched`** — a vendor silent on 1 filter of 3 outranks one silent on 2, and within each of those bands the priced/photo/distance keys apply exactly as they do above the divider. Only silences count: a contradiction is rank −1 and never reaches the list at all.
- **A rank-0 pin recedes hard on the map** — `PARTIAL_ICON_OPACITY` 0.22 / `PARTIAL_LABEL_OPACITY` 0.28 in `vendor-map.tsx` (was 0.45/0.55; dropped 2026-08-06 now that silence no longer excludes and the faded population is much larger). Measured on a render, the partial disc sits at 22% of a full-match pin's colour saturation against 45% before. The label goes fainter than the disc because text at low opacity fades its white halo too, so it stops being legible while still adding clutter. **The old "keep it above 0.4 so it still looks tappable" floor is deliberately gone** — tapping is unaffected (MapLibre hit-testing ignores opacity), and the compensation is the selection override below. If a pin ever reads as invisible on a dark basemap feature (a park, say), these two constants are the knob.
- **The SELECTED pin is always fully opaque, whatever its rank** — `selectionPaint()`, applied by `applySelection` alongside the layout pass. Opacity is a **paint** property while everything else about selection is **layout**, so it needs its own `setPaintProperty` loop; miss that and tapping a faded pin opens a card next to a ghost.
- **Silence NEVER excludes — there is no exception** (changed 2026-08-06). `rare` filters used to invert the rule, dropping silent vendors on the reasoning that a hotel running a shuttle would say so. That was quietly deleting most of the map on one tap (filtering photographers on "also shoots film" ruled out **233 of 274**; it is now 3 ruled out — the ones saying an explicit `false` — and 230 demoted), and it was wrong in exactly the case it meant to catch, since a vendor is silent far more often because nobody extracted the fact than because they lack the thing. `rare` is now a **UI badge only** ("Rare" in the filter sheet, warning that a filter will not narrow much); the matcher does not read it, and `buildSelection` no longer stamps it onto a spec. Consequence to expect: those filters now leave a large dimmed-pin population on the map and a long partial tier in the list, which is the honest picture.
- **`matched` is a FRACTION, not a count of misses**, and the two are not interchangeable. A mixed-type search is one query, so a venue judged on 3 attributes and a photographer judged on 2 both being "silent on 1" is 67% against 50% — and the feed interleaves them. With a single type filtered (the common case) the two orderings are identical, since every vendor shares the denominator. `matchedFraction()` in `lib/filters/match.ts`.
- **It sits at key 2 rather than being special-cased to rank 0** because it is already a no-op above the divider: a rank-1 row matched everything, so it scores 1, as does a row whose type carries no filters at all.
- **`filterMatch` / `filterMatchFor` are the counting form of `filterRank` / `filterRankFor`**, returning `{ rank, unknown, active }`; the rank functions are now thin wrappers, so there is still one implementation of the rules. `unknown` rises by at most 1 per filter — every branch that notices a silence also ends that filter's turn — so it can never exceed `active`. `scripts/test-filter-match.mjs` covers the arithmetic; it is the only executable check on the matching rules, so run it after touching that module.
- **`rank` is the only tier with a visible divider** — `"Partial matches in the area"`, drawn in `vendor-feed.tsx` where the list crosses from full matches (rank 1) to the ones a filter could not confirm (rank 0). Matched, priced and photo are **internal**: they rank vendors that all equally match what the couple asked for, so a break there would imply a distinction the couple never drew. A partial match is different in kind, and saying so is what stops those rows reading as matches. Rank −1 rows are excluded outright and never reach the feed.
- **The divider is derived from the RENDERED items, not from `entries`.** `useVendorPreviews` silently drops ids whose vendor row is gone; anchoring on `entries` means such a row can take the divider with it and leave everything below it reading as a full match. It is also drawn when it lands at the very top (every result partial) — odd as a "divider", but far better than presenting rows that match nothing as though they did.
- **`has_price` and `has_photo` are computed in SQL** (`0035`), for the same reason `approximate` is: the sort runs over the whole viewport **before** the feed pages 20 at a time, so the flags cannot come from the per-card fetch, which only ever sees the page already chosen. Two booleans is ~2 B/row against the 208 B/row `0034` measured.
- **The pricing tag is `vendors.filters`** — any **numeric** key whose name contains `price`. That is what makes it generalize across types without naming them (`price_min`, but also `bride_price_min` / `party_price_max` / `trial_price` for hair & makeup); a verbatim `price_quote` with no parsed number counts too. Deliberately **not** the string keys `price_basis` / `price_kind` / `price_confidence` — those describe a price rather than being one. Measured on the 2,163-row corpus: **818 (37.8%)**, a real split rather than a near-empty tier. **Hotels model no price at all** (the type has `block_type` and `min_rooms`, never a rate), so every hotel sits in the unpriced tier permanently; inside a category-filtered view they all tie and the sort falls through.
- **`has_photo` must NOT test `google_photos` strictly.** That column is a **lazy cache** filled on the first view of a vendor page (`lib/google-photos.ts`), so a null means nobody has looked yet — never that the vendor has no photos. Testing it strictly ranks vendors by whether somebody happened to open them, which is view history, not a fact. The SQL mirrors what `photoCandidates` in `vendor-preview-card.tsx` actually does: a non-empty array, **or** null-with-a-`google_place_id` (optimistic, the common case), **or** any active recon photo. An empty array is the one negative — resolved, and Google had nothing.
- **Both flags need `coalesce(…, false)`, and it is load-bearing.** They are OR chains over jsonb tests, and a jsonb test on a missing key yields NULL, so `false OR NULL` is NULL: without it the columns come back **NULL on exactly the rows that mean no**, and a later `not has_price` would match nothing. Found by running the migration, not by reading it. The client compares `=== true` for the same reason — that also makes a missing column (pre-`0035`) read as false for all rows alike, so both keys become no-ops and the order falls back to nearest-first rather than being corrupted by `NaN`.
- **The recon-photo `EXISTS` sits LAST in its OR on purpose.** The two cheap column tests are true for almost every seeded vendor and an OR stops at the first true, so the semi-join is skipped on the common path. Verified with `explain analyze`: **5 loops over 2,178 rows**, rising to exactly 305 once 300 rows were stripped of their `google_place_id`.

### The partial tier has to show up on EVERY counting surface
- Reported as "the filter says only 5 matches but the map and list show far more" (Kiara, 2026-08-06). Nothing was miscounted: the sheet footer said `5 matches on screen · 121 missing some info`, the pill said `126 results`, and 5 + 121 = 126. **Because silence never excludes, the partial tier is usually the majority of what is on screen** — 382 of 679 CO venues carry no price at all — so any surface printing a bare count of "what is showing" is printing that tier, not the answer. The pin fade and the feed divider were already doing the right thing; three other surfaces were not. **When you touch the matcher, walk every surface that renders a count or a list.**
- **Cluster bubbles count matches**, via a supercluster `clusterProperties: { matched: ["+", ["get","rank"]] }` on each per-type source (`rank` is 1/0 per point, so summing it counts matches). This was the surface that made the report so stark: at the zoom in the screenshot there are **no individual pins at all**, only bubbles, so the one signal that existed was invisible. The label is a three-way `case` — all leaves matched → `point_count_abbreviated` (so the unfiltered case is byte-for-byte what it always was, `1.2k` included), some matched → the match count, none matched → the abbreviated total, receded to the same `PARTIAL_ICON_OPACITY`/`PARTIAL_LABEL_OPACITY` an individual rank-0 pin gets. Free to keep current: a filter change already rebuilds the source through `applyVendors`.
- **The pill reads `N of M`, not `M results`**, and the full sentence lives in its `aria-label` — the chip shares a 390px row with the filter button and the view toggle, so anything longer truncates away exactly the number that was added.
- **A cluster tap passes `{id, rank}[]`, not `string[]`** (`ClusterOpenPayload.entries`), which is what lets the cluster feed draw the divider `VendorFeed` already knows how to render — it was handing over bare ids, so every row read as a full match. Its heading counts matches too. The `wr:cluster` sessionStorage payload changed shape with it, and the restore path still accepts the old bare-`ids` form as all-matches.
- **`basisScale` makes a stated assumption real.** `VENUE_PRICE_ASSUMPTIONS` (100 guests, 5 hours) was rendered in the sheet's footnote and used by **nothing**: the histogram binned a $150-per-person venue raw into the $0-499 bar while the matcher demoted that same venue for being silent on a price it had published. A `FilterDef.basisScale` map now converts a convertible off-basis quote in **both** readers, and a basis with no factor (`per_night` on a venue, or a caterer's per-person against a package slider) still reads as silence. Scaling goes **after** the season/day tier lookup (a tier is quoted in the vendor's own basis) and **before** the open-ended `OPEN_HI` sentinel, which is not a price and must never be multiplied.

### Migrations
- **Write idempotent:** `add column if not exists`; for constraints use `drop constraint if exists` then `add constraint` (Postgres has **no** "add constraint if not exists").
- **One ALTER per constraint** — you cannot chain multiple `add constraint` clauses in a single `alter table` (syntax error).
- **Not auto-applied** to the hosted DB — run new migrations by hand in the Supabase SQL editor.
- **No apostrophes or `$$` in SQL comments** — the Supabase SQL editor splits a paste into statements with a lexer that tracks string literals but does **not** skip `--` comments. A `'` in a comment (`the tier's rule`, `typo'd`) opens a phantom string; an odd number of them desyncs it, it stops seeing the dollar-quoted function boundary, and it splits the body at the semicolon inside it — the server then rejects the fragment (`42601: syntax error at or near "limit"`). Cost a failed hand-apply of `0026` on 2026-07-29 (7 comment apostrophes; `0025` had 2 and survived on even parity). Write comments apostrophe-free — "does not" over "doesn't", "the rule of the strict tier" over "the strict tier's rule" — and name the delimiter "dollar-quoted body", never the literal token. `psql -f` is immune, so **local testing will not catch this**; the check is `grep -n "'" <file> | grep -- "--"`.
- **Prefer single-quoted literals with DOUBLED apostrophes over dollar-quoting in hand-applied SQL** — same lexer, second way it bites (2026-08-07). Postgres itself prefers `$q$…$q$` for text full of apostrophes and dollar signs, but the editor lints **client-side, before the server ever parses**, and that lexer does not understand a dollar-quoted string. So every apostrophe *inside* one toggles its in-string state exactly like an apostrophe in a comment does. `scripts/fix-quote-only-residue.sql` carried 25 of them (`what's public`, `don't mention`) — odd parity again — which collapsed 75 statements into 36 fragments, 6 holding more than one `UPDATE`, and the editor then raised **"This query runs an UPDATE without a WHERE clause. It may update every row in the target table"** on a file where all 74 statements are gated on a single `id`. A false positive, but not one to click through on live data. Doubling (`don''t`) is the escape every SQL lexer agrees on. Safe whenever no value contains a **backslash** (nothing then depends on `standard_conforming_strings`); a `$` is inert inside a single-quoted string, so money figures need no special handling. The older `scripts/fix-comma-split-recon.sql` still uses `$fix$` — it predates this and is short enough that the parity never bit. **The check is the same shape as the comment one, and equally invisible to `psql -f`.**
